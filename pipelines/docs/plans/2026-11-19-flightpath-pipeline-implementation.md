# Flightpath Pipeline Implementation Plan

> **Execution:** follow owner/project Paseo policy and existing role assignments.
> Steps use checkbox (`- [ ]`) syntax for tracking.

Revised 2026-11-20. Replaces the 2026-11-19 draft of this file.

**Goal:** Build Pipeline, a standalone Paseo plugin that runs a project workflow written in GitHub-Actions-like YAML with its own runtime, evidence, rework, matrix fan-out, provider failover, recovery and UI.

**Architecture:** One saved workflow file per project, edited through a digest compare-and-swap. Start validates the workflow and the Start-form inputs, expands them into a job graph and writes a run snapshot; a pure event-sourced engine then drives the graph behind host ports (agents, checks, MCP) in one Git worktree per run. The client renders server-computed models only. Nothing depends on Plan or Roadmap.

**Tech Stack:** TypeScript 5.9, `@getpaseo/plugin` / `@getpaseo/client` / `@getpaseo/protocol` 0.17.0-beta.1, React 19.1 and React Native 0.81.5 (client), Zod 4, `yaml` 2 (server only), `@modelcontextprotocol/sdk` 1.32.2, Vitest 5, ESLint 10.

**Spec:** [`pipelines/docs/specs/2026-11-19-flightpath-pipeline-design.md`](../specs/2026-11-19-flightpath-pipeline-design.md)

## Global Constraints

- Status: approved to implement. Live sandbox verification follows the separate authorization in Task 7.
- Standalone: every task edits `pipelines/` only. No file in `plan/` or `roadmap/` changes, nothing is imported from them, and no code reads another plugin's data. Each task's verification ends with `git diff --stat -- plan roadmap` printing nothing.
- Plugin modules live only under `client/`, `server/`, `shared/`. `shared/` imports neither of the others. The client has no npm dependency beyond what the host provides, no DOM, no SVG library, no React Flow.
- The Pipeline server subprocess is the only writer of Pipeline plugin data: directories `0700`, files `0600`, temp file plus rename for replaceable files, no-clobber for write-once files.
- One saved workflow file per project. No numbered revisions, no historical copies, no version key in the YAML. Unknown input is rejected with a coded diagnostic, never repaired silently.
- Human authority exists only in UI RPC handlers. No MCP tool can start a run, save a workflow, apply a proposal, accept, approve, retry, choose a provider or grant a return.
- Git is read through plumbing with a temporary index file. Pipeline never runs `git worktree` or `git stash`, never updates a ref and never writes the real index; the run's one worktree is created by the host.
- Target Paseo 0.17. Pin the development SDK packages and host verification image to 0.17.0-beta.1. Prove each host capability in spec section 9 on that release.
- Tests use synthetic data, fakes and temporary directories. No real provider launch, plugin installation, daemon restart or host worktree creation without explicit owner authorisation.
- Repository text, identifiers, comments and UI strings are English. Product UI says "Acceptance criteria" for `done` items, "Accept" for one task or job and "Approve" for the `approval` job. Comments are sparse and never mention task numbers or stages.
- Tasks run in order 1 to 7. Each ends with its own verification and one commit, made only after approval and under the delivery policy. A passing suite is reported as validated only; review, installation and real UI verification are separate delivery states.
- Every task's verification also runs `npm --prefix pipelines run typecheck && npm --prefix pipelines run lint`, both exit 0. Dependencies are installed once in Task 1 with `npm --prefix pipelines install`, which touches `pipelines/` only.

- [ ] **Implement:**
  - `reduce` and `decide` are pure and deterministic: graph order, `max-parallel`, nothing while paused. Intents first: `create_workspace` and `create_agent` are emitted only for an intent already in the state; one attempt holds a binding, key and settings per role; the reviewer intent appears when the cycle reaches review.
  - Writer slot and evidence (spec 6.3): one slot holder per run, held by an `agent` or task attempt from its worker's start until its own checks and review end or it parks at `awaiting_human`; isolated checks only while no holder is active and only on one identity; a ready verifier before a new writer. `cycle.opened` fixes the identity; checks, the review bracket, Accept and Approve must match it; a mismatch gives `cycle.invalidated`, keeps the evidence as `late` and opens a new cycle; three unexplained invalidations fail the attempt with `worktree_unstable`; an isolated job whose group drifted becomes exclusive for the rest of the run. A reopened cycle repeats verification phases only, never a worker turn. Before a verification-only job (`checks`, `review`, `approval`) starts, before Approve and at an `open_cycle` with scope `"finish"`, each verification-only result relied on that was recorded on another identity is superseded (`evidence_stale`) and that job reruns with cause `stale`, no budget used. A succeeded writer result (`agent` job, task job, `agent` matrix instance) stays pinned to its own cycle identity and is superseded only by rework. `finish_run` follows only a finish cycle that left no verification-only result stale.
  - Attempts (spec 6.4): reminder then `no_result`; `outputs_invalid` after three rejections; task failures retry on the same target until `retries` is used; `manual` attempts are not counted; `human.changes_requested` on a job awaiting human acceptance starts a `manual` attempt with the note, and on an `approval` job without `rework` fails the job with the note; only the current successful attempt satisfies `needs` and resolves references.
  - Failover (spec 6.5): `attempt.ended` with outcome `provider_failed` uses no retry. With an unfailed fallback: `job.provider_switched`, then one attempt with cause `failover`, the target sticky for that job and role. Otherwise `job.needs_human` with the failure list; from there only `job.retry_requested { target }` starts one `manual` attempt. No other failure changes the target.
  - Barrier (spec 6.6): `quiesce.started` marks attempts stopping; `decide` emits `interrupt_agent` and `cancel_checks` and no retry, failover, rework or descendant start until `quiesce.confirmed`; `quiesce.unconfirmed` pauses the run; `run.cancelled` is reducible only after confirmation.
  - Rework (spec 6.7): counter per reviewing job, one `rework.started` carrying the superseded attempt ids, task ids required for a `run-tasks` target, the new target attempt only after the barrier, `rework_exhausted`, one extra return per `rework.granted`, `stale_attempt` for outcomes of superseded or stopping attempts.
  - `reconcile` (spec 6.8): intents without bindings resolve from `HostFacts` (one match binds; none repeats the same key or branch; several, or an unavailable lookup, pause with `binding_unknown`); open barriers resume; a `check.launched` process without evidence that `HostFacts` reports alive keeps the run paused until it is terminated and confirmed; lost attempts end as `lost` with one `run.paused` of reason `recovery`. It never emits a new key.
  - `resolveCommand` returns a shell string unchanged and resolves references in argv elements after the first, each staying one element; no value is ever concatenated into shell text. A resolved element with a NUL byte or over 4 KiB fails the job with `ref_value_invalid`.
  - Run store: `snapshot.json` no-clobber with `snapshotHash`; `findByStartKey` scans the project's snapshots on disk and keeps no separate index; `journal.jsonl` one synced line per record with a consecutive `seq`. The first append after opening repairs a torn last record by truncating to the last complete record. A bad record or a `seq` gap before the last record is never repaired: `load` reports `journal_corrupt` and `append` refuses.
- [ ] **Verify:** `npm --prefix pipelines test -- server/run-engine.test.ts server/outputs.test.ts server/commands.test.ts server/rework.test.ts server/recovery.test.ts server/run-store.test.ts` passes, including:

  - Evidence: drift between two check commands, during a review and while awaiting a human each invalidate the cycle; Accept on a changed identity fails with `evidence_stale`; a write after `lint` succeeded makes `lint` rerun before `review` or the finish can use it, with no retry consumed; with writers `a` then `b`, each accepted on its own identity, and `lint` between them, the finish refreshes `lint` once on the final identity, starts no attempt of `a` or `b`, emits `finish_run`, and a further `decide` yields no effect.
  - Roles and creation: distinct worker and reviewer bindings and keys; the same job and attempt number in two runs give different creation keys; a reviewer outcome on a worker binding is not reducible; an `agent.intent` without a binding never yields a second key; `reconcile` binds on one match and pauses with `binding_unknown` on none-and-unavailable and on several; the same for `workspace.intent`.
