- `TaskInput = z.object({ id: Id.optional(), title: z.string().min(1), description: z.string(),

### 1.3 Draft rules (`server/plans.ts` `draft`, one producer for UI and MCP)

Definitions: a request is **v2-shaped** when any task carries any of `dependsOn`, `parallel`,
`completion`, `grill`, `dod`. `bound` = the target plan exists and has `featureId`.

1. Origin and revision precedence unchanged: `store.transact(expectedRevision)` first
   (`revision_conflict`), then eligibility (`plan_ineligible`) as today.
2. `featureId` given → it must name an existing feature (`not_found` otherwise). No rule on the
   feature's status is added.
3. Binding (no downgrade, no silent rebind):
   - target plan bound and request `featureId` absent → `invalid_input` ("plan is bound to
     feature X; pass its featureId");
   - target plan bound and request `featureId` differs → `invalid_input` (no rebinding in R1);
   - target plan bound and `featureId` equal → v2 path.
4. Unbound target (new plan, or existing plan without `featureId`):
   - `featureId` given → v2 path; sets `plan.featureId` (binding);
   - no `featureId` and v2-shaped → `invalid_input` (feature binding required for v2);
   - no `featureId`, not v2-shaped → the shipped legacy path, byte-identical (same task objects
     `{ id, title, description }`, same body, `contentHash(body)`), see §7 C3.
5. v2 path: tasks are built explicitly as `TaskDefinitionV2 { id: t.id ?? newId(), title,
   description, dependsOn: t.dependsOn ?? [], parallel: t.parallel ?? false, completion:
   t.completion ?? "auto", grill: t.grill ?? false, dod: t.dod ?? "" }` (defaults constructed in
   code, never in a schema); task ids unique (`invalid_input`); `taskGraphIssues(tasks)` non-empty
   → `invalid_input` with `details.issues` (before the store schema would reject generically);
   revision `{ rev, createdAt, schema: 2, markdown, tasks, basedOn, decisionSnapshotHash }` with
   `contentHash: contentHashV2(body)`; `plan.title`, `plan.sessionIds` updated as today.
6. Supplied task ids are kept, so `taskStates` keyed by `(planRev, taskId)` keep resolving; earlier
   revisions, receipts, `approvals` and `taskStates` are never modified.
7. Any rejection writes nothing (single transaction; export only after commit).

### 1.4 Blockers (`server/plan-rules.ts`, `server/plans.ts`)

- `approvalBlockers(plan: Plan): ApprovalBlocker[]`: latest revision `isV2Revision` →
  `[{ code: "gates_not_available" }]`; otherwise (legacy latest or no revision) `[]`.
- `plan.get` returns `blockers: approvalBlockers(plan)`.
- `plan.approve`: at the position of today's inline guard (after UI origin, latest lookup and the
  `plan_revision_mismatch` revision check; before the content-hash check and any receipt write),
  `const blockers = approvalBlockers(plan)`; non-empty → `DomainError("plan_ineligible", …,
  { blockers })`. Same message text as today. Legacy approval and receipt shape unchanged.
- `server/plan-rules.ts` `basisCurrent` keeps `contentHashFor`.

### 1.5 `relatedTo` (create only)

- `FeatureCreate.input` gains `relatedTo: z.array(Id).optional()`. `FeaturePatch`,
  `FeatureUpdate`, `FeatureDependenciesSet` and the MCP tool schemas in `server/feature-tools.ts`
  are separate objects and are not changed (no leak by schema reuse).
- `features.create`: duplicates → `invalid_input`; unknown ids → `not_found`; stored as given
  (the new id cannot be referenced). No cycle rule (descriptive relation). No change to update,
  history kinds or MCP.

### 1.6 RED/GREEN acceptance (T first)

- Legacy draft (no `featureId`, no v2 fields; new plan and existing legacy plan): body, tasks and
  `contentHash` equal the shipped function's output byte-for-byte; no `schema`, no `featureId`.
- v2-shaped request without `featureId` → `invalid_input`, store byte-identical.
- `featureId` naming no feature → `not_found`, no write.
- New plan with `featureId` → rev 1 `schema: 2`, explicit defaults, `plan.featureId` set,
  `contentHash === contentHashV2(body)`.
- Binding an existing legacy plan → appended `schema: 2` revision; earlier revision objects,
  hashes, receipts and `taskStates` byte-identical.
- Bound plan: draft without `featureId` → `invalid_input`; with another `featureId` →
  `invalid_input`; with the same → v2 revision; never a v1 revision.
- Supplied task ids preserved across revisions; unknown `dependsOn`, self, duplicate and cycles →
  `invalid_input` with issues; stale `expectedRevision` → `revision_conflict`, no write.
- MCP `roadmap_plan_draft` with the same arguments yields the same revision (fields, hash) as the
  commands path; the strict schema still rejects `projectId` and unknown task keys.
- `plan.get` → `blockers: [gates_not_available]` for a v2 latest revision, `[]` for legacy;
  `plan.approve` of the v2 revision → `plan_ineligible` with the same list; precedence
  (origin, then revision mismatch) unchanged; no receipt written.
- `PlanView.safeParse` of a real `plan.get` value succeeds (client parse); `plan.list` carries
  `featureId` for bound plans only.
- `feature.create` with `relatedTo`: stored; duplicate → `invalid_input`; unknown → `not_found`;
  absent → `[]`; `feature.update` and MCP still reject `relatedTo`.
- Commit: `feat(plans): draft v2 revisions and blockers`.

### 2.3 Pure models (exported from `client/roadmap-screen.tsx`)

- `type FeatureAction = "open" | "edit" | "dependencies" | "defer" | "resume" | "cancel" |
  "delete" | "createRemoval"`.
- `featureActions(feature: Feature, features: Feature[]): FeatureAction[]`, in this fixed order and
  derived only from the current server commands:
  - `open`, `edit`, `dependencies`: always (the server allows card and dependency edits in every
    status);
  - `defer`: status ∈ {created, planned, executing};
  - `resume`: status `deferred` (target `statusBeforeDefer`);
  - `cancel`: status ∈ {created, planned, executing, deferred};
  - `delete`: `everStarted === false` and no other feature lists this id in `dependsOn`;
  - `createRemoval`: status `done`.
  No action changes `done` or `cancelled` status; there is no start, run, chat or progress action.
- `resumeTarget(feature: Feature): "created" | "planned" | "executing" | undefined`.
- `type FeatureRow = { id: string; title: string; kind: "feature" | "bug"; status: FeatureStatus;
  statusLabel: string; statusReason?: string; dependsOn: Array<{ id: string; title: string }>;
  relatedTo: Array<{ id: string; title: string }>; actions: FeatureAction[] }`.
- `featureRows(features: Feature[]): FeatureRow[]`: roadmap order exactly as given; dependency and
  relation titles resolved from the same list (an id not in the list shows the id itself).
- `moveFeature(order: string[], id: string, direction: "up" | "down"): string[] | null`: a full
  permutation with `id` moved one place; `null` at either edge or for an unknown id.
- `editPatch(feature: Feature, draft: { title: string; description: string }):
  { title?: string; description?: string }`: only changed fields (title trimmed); `{}` when nothing
  changed (no call is made).

### 2.4 Components

- `ActionButton({ label, onPress, theme, disabled?, primary?, danger? })`: a `Pressable` with
  `minHeight: TARGET_SIZE`, `minWidth: TARGET_SIZE`, `accessibilityRole="button"`,
  `accessibilityLabel={label}`.
- `FeatureForm({ mode: "create" | "edit", hostId, projectId, theme, compact, revision, feature?,
  initial?: { title: string; relatedTo: string[] }, onDone(featureId?: string): void, onCancel():
  void })`:
  - pins `revision` at open (`useState(() => revision)`), like `client/question-editor.tsx`;
  - create: title (required, trimmed), description, kind (`feature` | `bug`, create only); sends

    with `{ expectedRevision: pinned }`; no `dependsOn` (dependencies have their own contract);
  - edit: title and description only, sends `feature.update { featureId, patch: editPatch(...) }`
    with the pinned revision; kind is shown read-only.
- `RoadmapScreen({ hostId, projectId, theme, compact, features: Feature[], revision: number,
  onOpenFeature(featureId: string): void, onBack(): void })`:
  - one row per `featureRows` entry: title, kind, feature status chip (label and colour from
    §2.2), status reason, dependency titles; no built/not-built, aggregate or progress badge;
  - "New feature" opens `FeatureForm` (create); row actions per `featureActions`;
  - reorder: Move up / Move down send `feature.reorder { order: moveFeature(...) }`;
  - defer, resume, cancel send `feature.status.set { featureId, status }` with `deferred`,
    `resumeTarget(feature)` or `cancelled`; cancel and delete require a second confirming press;
  - dependencies: an inline picker of the other features (self excluded; current selection
    preselected), sending `feature.dependencies.set { featureId, dependsOn }` in roadmap order;
    unknown or cyclic results are the server's `not_found` / `relation_cycle`, shown by the hook;
  - delete sends `feature.delete { featureId }`;
  - every list action sends `{ expectedRevision: revision }` (the snapshot the row was rendered
    from), so a stale list gets `revision_conflict` and writes nothing;
  - compact: single column, every target `TARGET_SIZE`.

### 3.2 Pure helpers (`client/plan-format.ts`)

- `type TaskSpecView = { id: string; title: string; description: string; v2?: { dependsOn:
  string[]; parallel: boolean; completion: "auto" | "human"; grill: boolean; grillSessionId?:
  string; dod: string; dodItems: DodItem[] } }`; `taskSpec(task: TaskDefinition |
  TaskDefinitionV2): TaskSpecView` (`v2` absent for a three-field legacy task; `dodItems` from
  `parseDod`).
- `type TaskField = "title" | "description" | "dependsOn" | "parallel" | "completion" | "grill" |
  "grillSessionId" | "dod"`; `type TaskDiff = { kind: "added" | "removed" | "changed" | "moved";
  taskId: string; title: string; changes?: Array<{ field: TaskField; before: string; after:
  string }>; from?: number; to?: number }`; `type RevisionDiff = { schemaChanged: boolean;
  markdownChanged: boolean; tasks: TaskDiff[] }`.
- `revisionDiff(from: PlanRevision, to: PlanRevision): RevisionDiff`: tasks matched by `id`;
  `added` (in `to` only) and `changed`/`moved` in `to` order, then `removed` (in `from` only) in
  `from` order; `moved` when a common task's index differs (`from`/`to` 0-based); `changed` lists
  every differing field with display strings (arrays joined by ", ", booleans "yes"/"no", absent
  "—"); a legacy-to-v2 pair sets `schemaChanged` and reports the v2 fields as changed from "—".
  The decision basis (`basedOn`) is not compared (not in the approved R1.2 scope).
- `dodSourceLabel(source: "file" | "project" | "global" | "none"): string` → "dod template.md",
  "Project settings", "Global settings", "No template".
- `insertTemplate(current: string, template: string): string`: `template` when `current` is blank,
  else `current.trimEnd() + "\n" + template`; never called without an explicit press.
- `type TaskEdits = Record<string, { dod?: string; grill?: boolean }>` (keyed by task id; absent
  keys mean unchanged).
- `taskEditsChanged(revision: PlanRevisionV2, edits: TaskEdits): boolean`: true when any edited
  `dod` or `grill` differs from the revision's value.
- `draftTasks(revision: PlanRevisionV2, edits: TaskEdits): TaskInput[]`: the full task list in
  revision order, each mapped explicitly to the R1.0 `TaskInput` fields only: `{ id, title,
  description, dependsOn, parallel, completion, grill, dod }`, with `title`, `description`,
  `dependsOn`, `parallel` and `completion` copied verbatim and `dod`/`grill` taken from `edits`
  where present. `grillSessionId` is never sent and never invented (no `TaskInput` authority; no
  producer exists before R2.2; see §7 C7).

    to edit its tasks";

- **`decisionCancel` command (server):**
  - a non-UI origin gives `invalid_input` before the store is touched (the `blockAccept`
    pattern);
  - then one transaction, so a stale revision gives `revision_conflict` and writes nothing;
  - the reason is trimmed, and an empty result gives `invalid_input`;
  - a missing question gives `not_found`;
  - an already-cancelled ref gives `decision_cancelled`, whatever the block state;
  - **no frozen check**: accepted decisions can be cancelled;
  - it appends `{ id: newId(), ref, reason, at, actor: { kind: "human" } }`, with the actor taken
    from the origin and never from input;
  - question records, blocks and links are not touched.
  - Ids come from the same `newId` (ULID). A cancellation id lives only in `meta.cancellations`,
    so `link.delete`, which searches `meta.links`, can never remove it.
- **Read-only cancelled decisions (`server/sessions.ts`):**

    `question.answer`, `question.confirm`, `question.skip`, `question.discuss`, and
    `relation.add`/`relation.remove` whose `target` is the cancelled question;
  - order: `assertNotFrozen` first (a frozen cancelled question reports `block_frozen`), then
    `assertNotCancelled`.
- **Still allowed:**
  - relations whose target is open and whose parent or upstream is cancelled;
  - `question.create` depending on a cancelled question;
  - `supersedes`/`informs` links to or from it;
  - derived `validity`/`stale` set by propagation.

  There are no fake answers and no graph, visibility or staleness side effects.

## 8. Task R1.5: basis cancellation makes approval not current (owner Q33=1; actionable)

### 8.2 Interfaces (exact)

`server/plan-hash.ts`:

```ts
/** Refs of explicitly cancelled decisions. Empty for a v1 meta, which has no `cancellations`. */
export function cancelledRefs(data: { meta: { cancellations?: readonly Cancellation[] } }): ReadonlySet<RefKey>;
export function activeBasis(sessions: Session[], sessionIds: string[], cancelled: ReadonlySet<RefKey> = new Set()): Ref[];
export function basedOnSnapshot(sessions: Session[], sessionIds: string[], cancelled: ReadonlySet<RefKey> = new Set()): SnapshotEntry[];
export function decisionSnapshotHash(sessions: Session[], sessionIds: string[], cancelled: ReadonlySet<RefKey> = new Set()): string;
```

- **`cancelledRefs`** returns `new Set(cancellations.map((c) => refKey(c.ref)))`, or an empty set
  when `cancellations` is absent.
  - It accepts `RoadmapData` (v2) and any structurally compatible meta.
  - It never throws: dangling refs are already rejected at load time by `cancellationRefIssues`.
- **`activeBasis`** keeps `computeVisibility(sessions)` over the full graph, unchanged. It then
  drops refs whose `refKey` is in `cancelled`.
  - A cancelled question keeps its visibility, its validity and its effect on children.
  - Only basis membership changes.
- **`basedOnSnapshot`** and **`decisionSnapshotHash`** forward `cancelled` to `activeBasis` and
  `basedOnSnapshot` respectively.
- **Untouched:** `contentHash`, `contentHashV2`, `contentHashFor`, `BasisEntry`, `SnapshotEntry` and
  canonical serialisation.
- **Equivalence:** with the empty default, every function returns exactly what it returns at
  `d3e57bc`. Existing calls that omit the argument are therefore byte-identical.

`server/plan-rules.ts`:

```ts
export function eligibility(sessions: Session[], sessionIds: string[], cancelled: ReadonlySet<RefKey> = new Set()): { basis: Ref[] } | { error: DomainError };
export function basisCurrent(sessions: Session[], sessionIds: string[], revision: PlanRevision, cancelled: ReadonlySet<RefKey> = new Set()): { ok: boolean; reasons: string[] };
export function currency(sessions: Session[], plan: Plan, receipt: ApprovalReceipt | null, copyOnly: boolean, cancelled: ReadonlySet<RefKey> = new Set()): Currency;
```

- **`eligibility`** forwards `cancelled` to `activeBasis` and `basedOnSnapshot`. The rules are
  unchanged:
  - an unknown session is `not_found`;
  - an empty basis after exclusion is the existing `plan_ineligible` "no active questions". No
    empty-basis eligibility is invented;
  - every remaining entry must be `valid` or `skipped`, otherwise `plan_ineligible` with the refs.
- **`basisCurrent`** checks in this order:
  1. The content-hash reason, unchanged.
  2. `now` from `basedOnSnapshot(sessions, sessionIds, cancelled)`.
  3. The "became active" loop over `now`, unchanged. Cancelled refs are not in `now`, so they never
     report "became active".
  4. For each recorded `basedOn` entry, **first** `if (cancelled.has(key)) { reasons.push(`${key}
     was cancelled`); continue; }`, then the existing "is no longer active", answer rev,
     definition rev, validity and skipped checks.
  5. "decision snapshot changed" from `decisionSnapshotHash(sessions, sessionIds, cancelled)`. As
     today, it is added only when no other reason exists.

  Exact reason string: `` `${refKey(ref)} was cancelled` ``, for example `S1/q2 was cancelled`.
  A cancelled ref that is not in the recorded `basedOn` adds no reason.
- **`currency`**: the order is unchanged (no latest revision → `unapproved`; no receipt →
  `unapproved` or `unverified`; receipt mismatch → `not_current` "different plan content"). It
  then calls `basisCurrent(sessions, plan.sessionIds, latest, cancelled)`.
- `approvalBlockers` and `taskTransition` are unchanged.

Precedence:

| Where | Order |
|---|---|
| `plan.approve` | `plan_revision_mismatch` (rev) → blockers (`plan_ineligible` with `gates_not_available` for v2) → content hash → basis (`plan_not_current`, reasons include `<ref> was cancelled`) |
| one `basedOn` entry | the cancelled reason replaces "is no longer active" and every per-entry diff for that ref |
