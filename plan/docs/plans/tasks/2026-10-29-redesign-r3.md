### 1.3 Process port (`server/process-port.ts`, R3.3; canonical "Process port")

Installed facts: `execCommand` is `promisify(execFile)`; its `encoding` option is `BufferEncoding`
(no `"buffer"`) and its stdout is a `string`, so it is not used for byte-exact output.
`spawnProcess(cmd, args, { stdio: "pipe" })` returns `ChildProcessWithoutNullStreams`;
`terminateProcess(child)` sends `SIGKILL` on POSIX.

```ts
export type ProcessResult = { exitCode: number | null; signal: string | null; stdout: Buffer; stderr: Buffer; truncated: boolean; error?: string };
export interface RunningProcess {
  write(b: string | Buffer): void;
  end(): void;
  terminate(): Promise<void>;
  /** Settles exactly once: on `close`, on `error` (for example ENOENT), or fail-closed at most
   *  `TERMINATE_GRACE_MS` (1500 ms) after a termination when `close` never comes (R3 corrective). */
  result: Promise<ProcessResult>;
}
export interface ProcessPort {
  spawn(command: string, args: string[], opts: { cwd: string; env: NodeJS.ProcessEnv; maxBuffer: number; timeoutMs: number; signal?: AbortSignal }): RunningProcess;
}
export function nodeProcessPort(): ProcessPort; // spawnProcess + terminateProcess
export function gitBytes(port: ProcessPort, cwd: string, args: string[]): Promise<Buffer>; // exit 0 → stdout bytes, else throws
```

Output is collected as `Buffer` chunks up to `maxBuffer` (`truncated: true` beyond it, and the
child is terminated). Timeout and `signal` abort call `terminate()`; the result still settles once.
Git output is never decoded as UTF-8 before hashing; NUL-separated listings are split on the byte
`0x00`, and paths are compared as bytes (non-UTF-8 paths stay safe).

### 2.2 Interfaces

```ts
// shared/readiness.ts — pure
export type NotReady = { code: "feature_not_executing" | "run_not_running" | "start_unauthorised" | "approval_not_current"
  | "prerequisite_not_done" | "dependency_not_verified" | "parallel_not_granted" | "ceiling" | "not_todo"; taskId?: string };
export type ReadinessInput = { feature: Feature; features: Feature[]; run: ExecutionRun; plan: Plan; approvedCurrent: boolean; delegation?: StartDelegation; ceiling: number };
export function readyTasks(x: ReadinessInput): { ready: string[]; blocked: NotReady[] };
export function runBlockers(x: Omit<ReadinessInput, "run"> & { run?: ExecutionRun }): NotReady[]; // run-level checks only
export const ceilingReached = (t: TaskRun, ceiling: number) => t.failedCycles >= ceiling + t.extraBudget;
export function prerequisitesDone(feature: Feature, features: Feature[]): boolean;
```

Readiness per task (design §3.3, all required): feature `executing`; run `running`; start
authorisation (`ui`, or an existing, unrevoked delegation covering the feature); approval current
(latest revision, verified receipt, not reworked); every prerequisite feature `done`; every
dependency `verified`; the task run is `todo`; not at the ceiling; and if any other task run is
`claimed`, `in_progress`, `checks_pending` or `review_pending`, the task has `parallel: true`.
Approval alone never makes a task ready.

Commands in `server/runs.ts` (UI only unless stated; each run write appends a `RunEvent`; events are
never rewritten or truncated):

- `run.start { projectId, expectedRevision, featureId, profileRef? }`: the target is the
  feature's single bound plan (R2 guarantees at most one; duplicates fail with R2's
  `feature_has_multiple_plans`) at its latest revision, which must be approved and current. Feature
  `planned` → `executing` (status event, `everStarted: true`), or `executing` with no live run.
  **No unbound run (canonical "Start without a coordinator"):** with no `feature.coordinator` and no
  `profileRef` → `invalid_input` "choose a coordinator profile or bind an existing chat"; with a
  `profileRef` the coordinator is created in R3.4 (R3.1 accepts the field and refuses with
  `invalid_input` "coordinator creation arrives in R3.4" until then, so no unbound run is ever
  recorded in R3.1–R3.3). The run: `{ id, runToken: ulid, featureId, planId, planRev, state,
  startAuth: { kind: "ui", at }, tasks: one `todo` TaskRun per revision task, acks: [], events:
  [started], lateEvidence: [] }`; `state` `running`, or `paused` with `prerequisite_not_done`. A
  repeated start with a live run returns it (no second run). Refusals for run-level readiness →
  `run_not_ready { blocked }`.
- `run.pause { runId, runToken }`, `run.resume { runId, runToken }`: state changes and events here;
  agent steps are R3.5. Resume re-runs `runBlockers`; refused → `run_not_ready { blocked }`; a run
  paused for `deferred` cannot resume while the feature is deferred.
- `run.budget.grant { runId, runToken, taskId, cycles: 1..1000 }` (canonical "Budget reopening"):
  only while the task run is `ceiling`; adds `cycles` to `extraBudget` (never resets
  `failedCycles`), appends `budget_granted`, and sets `ceiling → todo` iff `failedCycles < ceiling +
  extraBudget` afterwards. Otherwise `invalid_input`.
- `delegation.revoke { delegationId }`: sets `revokedAt`; running work untouched.
- `run.get { runId }`, `run.list { featureId? }`: read only, with derived `ready`/`blocked`.
- Token: a run-scoped mutation whose `runToken` is not the run's token, or any mutation of an ended
  run → `run_stale`.

Guards in `server/plans.ts` (shared producers, so RPC and MCP inherit them):

- **Mid-run draft guard:** a draft of a bound plan whose feature has a run in `running` or `paused`
  → `plan_not_current` "revision is executing; stop and send for rework"; ended runs do not block.
  The DoD editor (`client/plan-view.tsx`) shows the server error text; no client change is needed
  in R3 (the editor already surfaces draft errors; verified in RED).
- **`verified` through the UI:** `task.update` to `verified` → `task_transition` exactly when an
  `ExecutionRun` exists with the addressed `planId` and `planRev` (any run state, ended included).
  Run-less revisions of the same plan and legacy plans keep the shipped UI verification.

`server/delegations.ts`: `recordDelegation(draft, { id, scope, featureId?, provenance, at })`
(appends a `StartDelegation` inside the caller's transaction and returns it),
`coveringDelegation(data, featureId)` (latest unrevoked delegation of the feature or the roadmap),
`delegatedStarts(data)` (synchronous **candidate prefilter**: features `planned` whose single bound
plan's latest v2 revision has a matching project approval copy, is not reworked and has a current
basis, with a covering delegation and no live run). Stored copies are not the approval authority:
every candidate is started through `run.start`, which verifies the durable receipt and currency
before writing (trust boundary kept; R3.4/R3.5 call it).

R3.1 interface decisions (as implemented): `createRunCommands(deps)` with `deps =
RoadmapServiceDeps & { approvals: ApprovalStore; settings: () => Promise<RoadmapSettings> }`
(ceiling = `repairCeiling`); writes `(open, input, origin)`: `start`, `pause`, `resume`,
`budgetGrant`, `revokeDelegation`; reads `(open, input)`: `get`, `list`; `createRunService(deps)`
wraps them for the UI. `run.start` returns `{ revision, runId, runToken, existing }`. A start
refused for currency is `run_not_ready { blocked: [{ code: "approval_not_current" }] }`; a feature
that is neither `planned` nor `executing` is `run_not_ready { blocked: [{ code:
"feature_not_executing" }] }`. Contracts in `shared/rpc-runs.ts` (`RUN_CONTRACTS`, `NotReady`,
`RunView`) and the route table `RUN_ROUTES`/`registerRunHandlers` in `server/run-handlers.ts` are

  <command>` item: identity before, spawn `/bin/sh -c <command>` (**technical choice**: check lines
  are human-authored shell lines approved with the revision), identity after; pass only with exit 0,

- `runReview(port, { command, worktree, request, timeoutMs, maxBuffer, signal })`: `reviewCommand`

  stdin then `end()`; parses `ReviewVerdict` from stdout; a spawn error, timeout, truncation,

  `reviewCommand` → task stays `review_pending` with `unresolved: ["no review command configured"]`.
- `shared/review-contract.ts`: zod `ReviewRequest { binding, dod: { items }, taskTitle, taskDescription }`,
  `ReviewVerdict { binding, verdict, items: Array<{ index, verdict, note }>, summary }`.
- `predicate(...) → "verified" | "pending" | "failed"`: all check items pass at the current
  binding; the review passes with every item; `completion: "human"` also needs `acceptance`.
- `task.accept { runId, runToken, taskId }` (UI): records `acceptance` evidence; only from
  `awaiting_acceptance`.
- Failure accounting: one complete failed cycle increments `failedCycles`; at `ceilingReached` the

### 4.2a Exact execution interfaces (Phase A completion, technical choices)

These close the five gaps in the R3.3 RED report. No new endpoint, MCP tool or agent-supplied
result; `Evidence`, `TaskRun`, `RunEvent` and `ResultBinding` keep their strict R0 shapes, and the
only model addition stays `ExecutionRun.evidence?: Evidence[]` (§1.1).

**Runner results (`server/check-runner.ts`, `server/review-runner.ts`):**

```ts
type Clock = { now?: () => Date; newId?: () => string };
export type CheckOutcome = {
  /** One per `- [check]` item, at the binding, `kind: "check"`, `itemIndex` = the item's `DodItem.index`. */
  evidence: Evidence[];
  /** Results that drifted or started off-binding: `lateReason: "worktree_drift"`. */
  late: Evidence[];
  result: "pass" | "fail";     // pass iff every item has a current pass and `late` is empty
};
export function runChecks(port: ProcessPort, x: Clock & { worktree: string; binding: ResultBinding; items: Array<{ index: number; command: string }>; excluded: string[]; timeoutMs: number; maxBuffer: number; signal?: AbortSignal }): Promise<CheckOutcome>;

export type ReviewOutcome = {
  status: "pass" | "fail" | "pending";   // pending only when no review command is configured
  /** One `kind: "review"` entry per review item (itemIndex), plus one overall entry without itemIndex. */
  evidence: Evidence[];
  late: Evidence[];
  reason?: string;                         // "no review command configured", parse or spawn failure text
};
export function runReview(port: ProcessPort, x: Clock & { command: string | undefined; worktree: string; request: ReviewRequest; excluded: string[]; timeoutMs: number; maxBuffer: number; signal?: AbortSignal }): Promise<ReviewOutcome>;
```

`excluded` is `[".decisions", <evidence directory if one is configured>]` and is passed to
`worktreeIdentity` for the before and after identities (gap 4) of both runners: a check or a
review that did not see the bound tree never passes, and a change while it ran makes its result
late (`worktree_drift`), even if the tree is restored before recording. `recordVerification`
additionally checks the current identity at the commit boundary. `TaskAccept` and
`RunEvidenceList` are in `RUN_EVIDENCE_CONTRACTS` (`shared/rpc-runs.ts`), registered with the run
routes in R3.5. `recordVerification` decides from the current cycle's own outcomes and evidence
(checks failed or late → failed; review missing or pending → `review_pending`; review failed or
late → failed; otherwise the predicate over this cycle's evidence), never from earlier cycles at
the same binding; the cycle's evidence ids are kept in a `cycle_evidence` `RunEvent` (detail
`<cycleId>|<ids>`), and `accept` judges exactly that cycle plus the acceptance.
`beginVerification` also requires `binding.contentHash` to equal the addressed revision's. Runner output is the only source
of check and review evidence; the runners never write the store.

**Predicate (`server/evidence.ts`, pure; gap 1):**

```ts
export type Verdict = "verified" | "pending" | "failed";
export function predicate(x: { task: TaskDefinitionV2; items: DodItem[]; binding: ResultBinding; evidence: Evidence[] }): Verdict;
// items = parseDod(task.dod).items (shared/dod.ts): kind "check" items are the check keys, kind "criterion" items the review item keys.
```

Only evidence of `task.id` whose `binding` deep-equals `binding` counts; within it the **latest**
entry (array order, which is append order) per key decides, so an old pass never masks a later
failure. Keys: each check item index; each review item index; the overall review (no
`itemIndex`); and for `completion: "human"` the acceptance. Any latest `fail` → `failed`; else any
missing key → `pending`; else `verified`. An empty DoD still needs the overall review pass. A new
cycle appends a fresh entry for every key it evaluates, so a passing cycle replaces the latest
values of an earlier failed cycle at the same binding. An acceptance counts only when it was
appended after the latest overall review pass (it accepts the current cycle's result, never an
earlier one).

**Internal result processing (`server/runs.ts`, not an RPC and not an MCP tool; gap 2):**

```ts
/** in_progress or review_pending → checks_pending: records the binding and opens a new server-owned cycle. */
beginVerification(open, x: { projectId: string; runId: string; runToken: string; taskId: string; binding: ResultBinding }): Promise<Result<{ revision: number; cycleId: string }>>;
/** Records one cycle's runner outcomes in one revalidating transaction. */
recordVerification(open, x: { projectId: string; runId: string; runToken: string; taskId: string; cycleId: string; binding: ResultBinding; checks: CheckOutcome; review?: ReviewOutcome }): Promise<Result<{ revision: number; state: TaskRunState }>>;
```

- Callers never supply cycle authority: `beginVerification` generates `cycleId` with `deps.newId`
  inside its transaction, stores `RunEvent { kind: "cycle_started", taskId, detail: cycleId }` and
  returns it. `recordVerification` appends
  `cycle_recorded` with the same detail; a second call with that `cycleId` changes nothing and
  returns the current state (idempotence; no new field).
- **Current identity at the commit boundary** (design §3.5 "current binding"): `RunDeps` gains an
  injected, server-owned reader
  `identity?: (x: { projectId: string; run: ExecutionRun; feature: Feature }) => Promise<WorktreeIdentity | { notReady: "unmerged" } | null>`
  (production: resolve the bound coordinator's worktree and call `worktreeIdentity(port, dir,
  excluded)`; tests: a fake). `recordVerification` reads it immediately before its transaction; a
  missing reader, `null`, `notReady` or an identity that differs from `x.binding.worktree` sends
  every evidence item to `lateEvidence` (`lateReason` `"identity_unavailable"` or
  `"worktree_drift"`) with no state change. `beginVerification` checks the same way that
  `x.binding.worktree` is the current identity and refuses (`invalid_input`, no write) otherwise.
- Revalidation inside the transaction: the run is `running` with `runToken`; the task run is in
  `checks_pending` or `review_pending`; `taskRun.binding` deep-equals `x.binding`; the cycle was
  started and not yet recorded. If any of these fails, every evidence item goes to `lateEvidence`
  (`lateReason`: `"run_stale"`, `"run_paused"` or `"binding_changed"`) and no state changes.
- Otherwise `checks.evidence` and `review.evidence` are appended to `run.evidence`, and
  `checks.late`/`review.late` to `lateEvidence`. Then `predicate` runs on the run's evidence:
  - `verified` → task run `verified`; the plan `TaskState` for `(planId, planRev, taskId)` becomes
    `verified` with `verification { at, note: "verified by checks and review" }` (this is the only
    writer of `verified` for run-managed revisions, §2.2);
  - `pending` with checks and review passed and `completion: "human"` → `awaiting_acceptance`;
  - `pending` because `review.status === "pending"` (no review command) → `review_pending` with
    `unresolved: ["no review command configured"]`; the cycle is recorded but **not counted as
    failed**. Once a command is configured, the server retries through the same
    `beginVerification` (allowed from `review_pending`; a new `cycleId`; the binding re-checked
    against the current identity). No automatic retry, no new RPC or authority;
  - `failed` (a complete cycle: checks failed, in which case review is not run and `review` is
    omitted, or review failed) → `failedCycles += 1` once per `cycleId`, `cycle_failed` event; if
    `ceilingReached` → `ceiling` and `ceiling_reached`, else back to `in_progress` with the same
    `agentId` for repair (**technical choice**: the claiming worker keeps the task).
- Agent reports never reach this path: R3.4 tools may only call `beginVerification` through
  `roadmap_task_progress { state: "done" }`; evidence comes only from the runners.

**Acceptance and listing (gap 5):**

- `accept(open, { projectId, expectedRevision, runId, runToken, taskId }, origin)` (UI only,
