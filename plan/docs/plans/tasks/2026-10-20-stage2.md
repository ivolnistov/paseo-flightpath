## Rulings applied

1. **Server hand-rolled; protocol acceptance uses the official MCP SDK client.**
   - The endpoint is a minimal MCP server over streamable HTTP (stateless JSON responses), the
     same shape as the working excalidraw plugin: `initialize`, `ping`, `tools/list`,
     `tools/call`, and notifications answered with 202. Tool input JSON Schemas come from
     `z.toJSONSchema` (Zod 4, already a dependency). No runtime MCP dependency is added.
   - As the approved plan requires, the protocol integration test (T2.6) drives the endpoint
     with the official client from the `@modelcontextprotocol/sdk` package: `Client` plus
     `StreamableHTTPClientTransport`. It is added as a **devDependency** pinned to `1.32.1`, the
     current `latest` per a read-only `npm view` on the configured registry
     (`https://registry.npmjs.org/`) on 2026-10-20.
   - P2 adds that devDependency at P2.4 time through the existing npm config, with no registry
     or config change.
   - Raw `fetch` is used only for transport-security cases the SDK client cannot express:
     Host/Origin, 404 uniformity, 405, 413 and malformed JSON.
2. **URLs are bound to a project, not a path.** Path is `/mcp/<grantId>.<sig>`, where
   `sig = base64url(HMAC-SHA256(secret, "v1\n" + grantId + "\n" + projectId))`. The grant record
   (plugin-data, outside the project) holds `projectId`, the resolved `storeRoot` and attribution.
   A request is accepted only when a grant exists, its signature verifies in constant time over
   the grant's own `projectId`, and the root still passes the safety checks. Editing a project
   file can never widen access.
3. **Root resolution stays server-authoritative on every call; holder hydration (E1 resolved
   for installed 0.12.0).**
   - **Installed types:**
     - `PluginServerContext` has no `paseo` member: `@getpaseo/plugin/dist/server/contracts.d.ts:24-28`.
     - `PluginHandlerContext { paseo }`: `contracts.d.ts:8-10`.
     - `PluginHookContext { paseo; signal }`: `lifecycle.d.ts:5-15`.
   - **Host runtime (E1, verified read-only in the installed daemon `@getpaseo/server`
     `dist/server/server/plugins/plugin-process.js`):**
     - There is one module-level `paseo` per plugin subprocess, created in `initialize()`
       (`:220-231`) over a reconnecting IPC `DaemonClient`.
     - `contribute()` receives only `handle`, `registerProvider`, `registerUsageSource`,
       `registerSettings`, `on` and `before` (`:236-244`). **No public start-time acquisition
       exists.**
     - Every RPC handler (`:443`) and every hook (`:463`) receives that same instance.
     - It is disposed once, in `shutdown()` (`:270-289`).

     A captured `context.paseo` is therefore valid for the plugin subprocess lifetime. This is
     outside the public type contract: **re-verify on any Paseo upgrade** before shipping
     (OVERVIEW notes this as a maintenance check).
   - **Hydration sources** (each only calls `holder.set(ctx.paseo)`):
     - every RPC handler;
     - `before("agent.create")`;
     - `before("agent.session_open")`, which returns `undefined`, so it makes no env or config
       change;
     - `on("agent.turn_started")`.

     Per the evidence summary in `docs/research/2026-10-20-stage2-host-runtime.md`, the daemon
     emits `turn_started` for any turn (UI, CLI, schedule or heartbeat). So after a reload the
     next ordinary agent turn hydrates the holder without the UI.
   - **No ordering claim.** Hook fan-out is asynchronous. The cards do **not** assume
     `turn_started` or `session_open` completes before that turn's tool calls. A tool call that
     finds the holder empty (a cold plugin with no RPC or hook since load, or the mid-turn race)
     **fails closed**:
     - result `isError: true` with text
       `not_ready: decision roadmap is starting; retry this tool call in a few seconds (opening the roadmap panel also makes it ready)`;
     - no directory lookup and no store access;
     - the persisted grant root is **never** used to open a store.
   - When ready, every `tools/call` resolves `grant.projectId → projectRootPath` through
     `resolveProject(projectDirectoryFromPaseo(holder.get()), projectId)`. The store enforces
     `manifest.projectId === projectId`. The grant's `storeRoot` is only an equality
     cross-check (`project_mismatch`).
   - **Coordinator ruling (recorded):** this bounded transient not-ready state, with normal-turn
     hydration, preserves the approved root-security and reload semantics. No new owner
     decision is needed.
4. **Opt-in scope (Q2).** Inject only when all of these hold:
   - the provider is in the MCP allowlist `claude | codex | opencode | copilot`;
   - `config.mcpServers["decision-roadmap"]` is absent;
   - `config.cwd` maps to a registered project;
   - that project's store `version()` is `status: "ok"` with `disabled === false`.

   Missing, invalid or disabled stores get no injection. The hook is **fail-open**: any error
   returns `undefined` and is logged without secrets.
5. **No approval and no deletion from MCP.** The tool list has no approve, skip, init, delete,
   link-delete or tracker tool. A test asserts the exact tool name set.
6. **Chat writes are agent writes; no agent-id inference.** MCP mutations record
   `source: "chat"` and `actor: { kind: "agent" }`, **without `agentId`**.
   - The before-hook cannot know the agent id.
   - Correlating a later `agent.created` by provider and cwd can misattribute simultaneous
     creations that complete out of order.
   - No supported public agent-detail field was verified to expose the injected MCP URL.

   So the plugin does not bind grants to agents and never guesses. Grant isolation (project
   scope) is unaffected. Answers and confirmations require a non-empty `quoted` human text.
   `Answer.actor.agentId` stays optional in the model for a future verified binding.
7. **Port fallback invalidates old URLs.** On `EADDRINUSE` for the persisted port, the endpoint
   binds a fresh port and persists it. Every grant issued for the old port is marked
   `stale: true`. One log line gives the old and new port, the count of stale grants and their
   fingerprints, and the instruction "agents created before this change lose roadmap tools;
   recreate them". Agent ids are not known (ruling 6). Stale URLs fail at the TCP level; nothing
   can repair them in 0.12.0 (Contract 2).
8. **Redaction.** Logs never contain the secret, a signature, a full URL, quoted text, answer
   text or note text. A grant is identified in logs by `fp = sha256(grantId).slice(0, 8)`. Tool
   calls log `tool`, `fp` and the result `code` only.
9. **Plan tools gated until Stage 3 (integration dependency, not dropped).**
   - SPEC §8 approves `roadmap_plan_draft`, `roadmap_plan_status` and `roadmap_task_update`.
     They need `server/plans.ts`, which Stage 3 Task 3.1 creates, so Stage 2 does not register
     or stub them.
   - `buildTools(commands, extra?: McpToolTable)` takes an optional extension table. Stage 3
     passes the three plan tools through it and extends `TOOL_NAMES` with
     `STAGE3_TOOL_NAMES = ["roadmap_plan_draft", "roadmap_plan_status", "roadmap_task_update"]`.
   - The Stage 2 test asserts that these names are absent now. Stage 3 acceptance must add them
     and still assert that no approve tool exists.
   - `roadmap_task_update` must reject `verified` (SPEC §8).
10. **Grant cleanup limitation (bounded, documented).** Without agent binding,
    `agent.archived` cannot identify an agent's grants. Grants are removed only by the cap
    (1000, stale first, then oldest) and kept otherwise. A grant of an archived agent stays
    valid for its project until the cap evicts it or the port changes. Its URL was only ever
    held by that agent's configuration, and it grants no more than project-scoped roadmap
    access. OVERVIEW states this limitation. No private API is used.

### P2.4 Endpoint (`server/mcp-endpoint.ts`)

```ts
export interface McpEndpoint {
  port: number;
  urlFor(grant: Grant): string;               // http://127.0.0.1:<port>/mcp/<grantId>.<sig>
  close(): Promise<void>;                         // closes server and all connections; idempotent
}
export interface EndpointDeps { state: McpState; tools: McpToolTable; resolveGrant: GrantResolver;
  log: (m: string) => void; host?: "127.0.0.1" }
export type GrantResolver = (grant: Grant) => Promise<StoreOpener>; // re-checks root; throws DomainError
export async function startMcpEndpoint(deps: EndpointDeps): Promise<McpEndpoint>;
export function signGrant(secret: string, grantId: string, projectId: string): string;
export function verifyGrantPath(secret: string, key: string, lookup: (id: string) => Promise<Grant | null>): Promise<Grant | null>;
```
Request pipeline, each step answering exactly as listed:
1. If `Host` is not `127.0.0.1:<port>` or `localhost:<port>` → 403. Any `Origin` header → 403.
2. The path must match `^/mcp/([A-Za-z0-9_-]{1,64})\.([A-Za-z0-9_-]{43})$`, else 404. If the
   grant is missing or `stale`, or the signature check over `(grantId, grant.projectId)` fails
   (`timingSafeEqual` on equal-length buffers) → 404 with the same body, so the reason cannot be
   probed.
3. Non-POST → 405 with `Allow: POST`. Body over 1 MiB → 413. Invalid JSON → 400 with JSON-RPC
   −32700.
4. JSON-RPC (single or batch):
   - `initialize` → `protocolVersion`, one of `["2025-06-18","2025-03-26","2024-11-05"]`, echoing
     the requested version when supported. `capabilities: { tools: { listChanged: false } }`,
     `serverInfo: { name: "paseo-decision-roadmap", version }`, and `instructions` = the
     tool-usage text in P2.5.
   - `ping` → `{}`.
   - `tools/list` → the table.
   - `tools/call` → see P2.5.
   - Unknown method → −32601. Notifications → no entry; all-notification bodies → 202.
5. `tools/call` resolves the opener with `resolveGrant(grant)` **per call**. A `DomainError`
   A `NotReadyError` (holder empty) becomes `isError` with the exact `not_ready:` text from
   ruling 3, and the endpoint makes no other call. A `DomainError`
   (`unsafe_root`, `project_mismatch`, `unknown_project`) becomes a tool result with
   `isError: true` and `code: message`. Unexpected errors → `isError` plus "internal error",
   with the stack logged.
6. Start: `loadOrCreateEndpoint()`. `listen(saved.port)` on `127.0.0.1`. On `EADDRINUSE`:
   `listen(0)`, `saveEndpoint({ ...saved, port: new })`, `markStale(saved.port)`, and log
   `MCP port changed <old>→<new>; <n> grants stale (fp: <fp,…>); agents created before this change lose roadmap tools; recreate them`.
   Other listen errors reject, and the caller logs them. A first start (no file) listens on 0
   and persists.

`GrantResolver` is built by exported `createGrantResolver` in `server/mcp-grants.ts` and used unchanged by `index.server.ts` and T2 support. Its deps are `{ holder: ReturnType<typeof createPaseoHolder>; directory: (p: PaseoApi) => ProjectDirectory; log: (m: string) => void; storeOptions?: Omit<StoreOptions, "storeRoot" | "projectId"> }`; return type is `GrantResolver`. Pass optional `storeOptions.fs` to `resolveProject` as well as `openStore`, allowing recording-FS tests to cover the real safety boundary. T2 GREEN replaces its inline resolver with this factory and removes the temporary state-log cast after P2 adds typed `log`. P2 owns production only. Logical body:

```ts
grant => {
  const paseo = holder.get();
  if (!paseo) throw new NotReadyError();   // exported from mcp-endpoint.ts; before any directory or fs access
  const { storeRoot } = await resolveProject(projectDirectoryFromPaseo(paseo), grant.projectId); // server-authoritative
  if (storeRoot !== grant.storeRoot) throw new DomainError("project_mismatch", "project root changed since injection");
  return (projectId) => projectId === grant.projectId
    ? Promise.resolve(openStore({ storeRoot, projectId, log }))   // store enforces manifest.projectId
    : Promise.reject(new DomainError("project_mismatch", "grant is bound to another project"));
}
```
`PaseoHolder.set` keeps the first captured instance and replaces it only if a later context
carries a different object, logging "paseo context replaced".

### P2.5 Tools (`server/mcp-tools.ts`)

```ts

export type McpToolTable = readonly McpTool<z.ZodType>[];
export function buildTools(commands: RoadmapCommands, extra?: McpToolTable): McpToolTable; // extra = Stage 3 plan tools
export const TOOL_NAMES = ["roadmap_overview", "roadmap_get_session", "roadmap_create_session",

```
Every input object is `.strict()`. `projectId` is **never** an argument: the endpoint injects it
from the grant. `origin = { source: "chat", actor: { kind: "agent" }, quoted }` (ruling 6).

| Tool | Arguments | Delegates to |
| --- | --- | --- |
| `roadmap_overview` | `{}` | `commands.overview` |
| `roadmap_get_session` | `{ sessionId }` | `commands.sessionGet` |
| `roadmap_create_session` | `{ expectedRevision, title }` | `commands.sessionCreate` |
| `roadmap_ask` | `{ expectedRevision, sessionId, questions: QuestionBatchInput["questions"] }` (1..20; option ids match `OptionId`) | `commands.questionCreateBatch` |
| `roadmap_answer` | `{ expectedRevision, sessionId, questionId, optionId?, text?, quoted: string.min(1), note? }` | `commands.questionAnswer` |
| `roadmap_confirm` | `{ expectedRevision, sessionId, questionId, quoted: string.min(1) }` | `commands.questionConfirm` |
| `roadmap_discuss` | `{ expectedRevision, sessionId, questionId, text: string.min(1) }` | `commands.questionDiscuss` |
| `roadmap_relate` | `{ expectedRevision, action: "add" \| "remove", relation: RelationInput }` | `relationAdd` / `relationRemove` |
| `roadmap_update_question` | `{ expectedRevision, sessionId, questionId, patch }` (same patch schema as `QuestionUpdate`) | `commands.questionUpdate` |
| `roadmap_link` | `{ expectedRevision, kind: "informs" \| "supersedes", from: LinkEnd, to: LinkEnd, note? }` | `commands.linkCreate` |

- Result mapping:
  - `ok` → `{ content: [{ type: "text", text: JSON.stringify(value) }] }`. The value carries the
    new `revision`; read tools include `revision` from their view.
  - `!ok` → `{ isError: true, content: [{ type: "text", text: "<code>: <message>" }] }`. For
    `revision_conflict` the text appends `Re-read with roadmap_overview or roadmap_get_session
    and retry with the current revision.`
- Argument parse failure → `isError` with "Invalid arguments: <path: message; …>". The values
  are not echoed.
- Descriptions must state:
