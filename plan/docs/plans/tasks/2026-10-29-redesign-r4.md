- **Installed SDK anchors** (0.12.0, read locally; the installed declarations are authoritative):
  - `timeline.subscribe(handler)` returns `TimelineSubscription = (() => void) & { readonly ready:
    Promise<void>; readonly subscriptionId: string | null; release(): Promise<void> }`
    (`@getpaseo/client/dist/connection/index.d.ts:44-48`).
    - It delivers live events only; `ready` rejects if establishment fails.
    - `subscription_restored` precedes later updates after a reconnect, and no history is
      fetched automatically.
    - A `replacement` invalidates the previous epoch; an `error` releases the observation
      (`client/dist/index.d.ts:250-258`).
  - Events are `PaseoAgentTimelineEvent` (`client/dist/index.d.ts:219-237`): an `agent_stream`
    payload, `{ agentId, event: { type: "replacement", epoch } }`, `{ agentId, subscriptionId,
    event: { type: "subscription_restored" } }`, or `{ agentId, event: { type: "error", error } }`.
    - The `agent_stream` payload is `{ subscriptionId?, agentId, event, timestamp, seq?: number,
      epoch?: string }` (`protocol/dist/messages.d.ts:9339-9410`).
    - Its `event.type: "timeline"` carries `{ provider, item, turnId? }`; `"permission_requested"`
      carries `{ provider, request: AgentPermissionRequest }`.
  - `timeline.refetch(options)` with options `{ direction?: "tail" | "before" | "after"; cursor?:
    { epoch: string; seq: number }; limit?; projection?: "projected" | "canonical"; requestId? }`
    (`client/dist/index.d.ts:191-197`; request schema `protocol messages.d.ts:2676-2695`).
    - It returns `FetchAgentTimelinePayload` with `epoch`, `reset`, `staleCursor`, `gap`, `window
      { minSeq, maxSeq, nextSeq }`, `startCursor`/`endCursor: { epoch, seq } | null`, `hasOlder`,
      `hasNewer` and `entries[]` (each `{ provider, item, turnId?, timestamp, seqStart, seqEnd,
      … }`) (`protocol messages.d.ts:12325-12360`).
    - `FetchAgentTimelineCursor = NonNullable<FetchAgentTimelinePayload["startCursor"]>`, i.e.
      `{ epoch, seq }` (`client/dist/daemon-client.d.ts:342`).
  - **Permissions:** `AgentPermissionRequest.id` (`protocol agent-types.d.ts:408-420`) is the
    `requestId` of `respondToPermission({ requestId, response })`.
- **Order** (root ruling 2026-10-29, from Fable's read-only review): subscribe → await `ready` →
  refetch → merge → replay the buffer → (on agent change or unmount) release. No event is lost
  between history and live.
  1. `subscribe(handler)` first. Events received before history is merged are buffered.
  2. Await `ready`. On rejection: `status: "error"`, no refetch.
  3. `refetch({ direction: "tail", projection: "canonical", limit: 200 })`. `canonical` is the
     server timeline projection, not plugin state. Remember `epoch` and `endCursor`.
  4. Merge the entries by `seqStart`/`seqEnd`. Replay buffered `agent_stream` events: an event
     whose `epoch` differs from the merged epoch is dropped, and an event whose `seq` is at or below
     the merged `endCursor.seq` is a duplicate.
- **Reconnect and errors:**
  - `subscription_restored` → `refetch({ direction: "after", cursor: lastEndCursor, projection:
    "canonical" })`, then merge.
    - A reply with `reset`, `staleCursor` or `gap` → drop the entries and refetch the tail.
  - `replacement { epoch }` → drop the old epoch's entries and refetch the tail.
  - `error` → `status: "stale"`. The host has released the observation; call `release()` locally
    (idempotent) and offer reload.
- **Verified gaps** (RED preflight must pin them; not invented here):
  - whether a live `agent_stream` `seq` equals the `seqEnd` of the entry a later refetch returns;
  - how an `agent_stream` event without `seq` (optional) is ordered. The planned handling is to
    render it as transient until the next merge.
- An agent change or unmount releases the subscription. A null `agentId` → empty, no SDK call.
- **`FeatureChat({ hostId, projectId, feature, theme, compact })`:**

- **Implementation choices (R4.1 GREEN; root-accepted T choices):**
  - **Projection:** the installed server returns projected entries whatever projection is
    requested (`session.js:5863` sets `"projected"`). `mergeTimeline` is range-authoritative: a
    next entry replaces every previous row its `[seqStart, seqEnd]` overlaps, the newer one wins,
    the result is ordered purely by `seqStart`, and rows without numeric seqs are dropped.
  - **Live folding** mirrors the projection so a stream does not render as fragments:
    - a tool-call update with the same `callId` and turn replaces its row;
    - an assistant or reasoning chunk extends the previous row of the same kind only when the seqs
      are contiguous and both carry the same `turnId` (and no conflicting `messageId`);
    - a live `seq` at or below the last row, or inside a projected range, is a duplicate. A live
      seq is never assumed to equal `seqEnd`.
  - **No-seq live events** go into an optional `transient` field. They never displace or reorder
    seq rows, and the next canonical merge clears them.
  - **Hook state:** `{ entries, status: idle|loading|live|stale|error, error?, transient? }` plus
    `reload()`. A refetch generation counter ignores stale replies, and an agent change or
    unmount stops all callbacks.
  - **`FeatureChat`:**
    - reads the live run directly (`useRpc(RunList)` + `useQuery` under `roadmapKey(…, "runs",
      featureId)`), because the R4.2 run hooks do not exist yet;
    - Pause/Resume go through `useRoadmapMutation` (latest cached revision, the current
      `runToken`, refusal toast and invalidation);
    - permissions are state, filled from the coordinator handle's `pendingPermissions` (a snapshot
      mirror, `null` until a snapshot arrives; `client/dist/index.d.ts:260-302`) on mount, after
      `refresh()` and on every `handle.subscribe` agent update. `useAgent` snapshots carry no
      permissions (`plugin contracts.d.ts:36-53`), so it cannot be used for this;
    - a failed send shows "Not sent: …", keeps the text, and is not retried.
  - Neither module is wired into the feature screen or any client entry yet (R4.2), so nothing
    here claims a live or current-client use.
- **R4.1 corrective (independent verification D1–D4):**
  - **D1:** the `subscription_restored` refetch has no `limit`. The installed server returns every
    row after the cursor (`session.js:5864-5865`), and any page still reporting `hasNewer` is
    followed from its `endCursor` before the buffered live events replay. The tail keeps

    - The change resets the per-context `sending`, send error and permission error; the draft is

    - Send and permission outcomes are applied only while mounted and in the same generation.
  - **D4:** the plugin's own rows render through `DecisionTimelineCard` and `RunTimelineCard` when

    - The card gets the real `agentId`, the row timestamp, the theme, `host { id: hostId, label:
      hostId }` and `layout { compact, platform }` (`Platform.OS`, mapped to ios, android or web).
    - Unknown, malformed or other-version rows show "Plugin row not shown (kind vN)".
    - The host offers no generic renderer for a plugin-owned list.

- **Truth sources** (root ruling):
  - Approval currency and the receipt come from `plan.get` of the feature's single bound plan,
    never a UI guess or a plan-list summary.
  - Acknowledgements, readiness, blockers, the current `runToken` and the store revision come from
    the latest `run.get`. Every run write uses that `runToken`.
  - A refusal (`run_stale`, `run_not_ready { blocked }`, `revision_conflict`, a state
    `invalid_input`) is shown as text and refetches; nothing is retried silently.
- **Control → contract** (enablement mirrors design §3.6 and accepted R3; no new policy):
  - **Start:** feature planned or executing, `approvalCurrent`, no live run → `run.start`.
    Without a binding the profile picker is required (`profileRef`); with a binding, no profile.
  - **Pause / Resume:** live run running / paused → `run.pause` / `run.resume` (`runId`,
    `runToken`).
  - **Stop and rework:** `approvedLatest` and feature planned or executing → `plan.rework { planId,
    planRev: latest, reason }`, with a required reason (a live run ends server side).
  - **Defer / Cancel:** the existing R1 feature actions (`feature.status.set`); not duplicated.
  - **Replace coordinator:** a coordinator is bound, and either there is no live run, or the live
    run is paused with no `awaiting ack` line → `coordinator.replace { featureId, profileRef }`
    (feature-scoped, no run token).
    - A running run gives the reason "pause the run first".
    - A paused run with awaiting acks gives the reason "waiting for acknowledgements".
  - **Grant budget:** a task with `atCeiling` → `run.budget.grant { runId, runToken, taskId,
    cycles }` (integer 1–1000).
  - **Accept:** a task `awaiting_acceptance` → `task.accept { runId, runToken, taskId }`.
  - **Open chat:** shows `FeatureChat` (R4.1).
- No control interrupts or cancels an agent.
- **Plan-view alignment:** `allowedTaskTargets` / the plan view never offer `verified` for a
  revision that a run manages. That is true when a run of the feature has the same `planId` and
  `planRev`, in any state, which is exactly the server's refusal rule. Non-run revisions keep
