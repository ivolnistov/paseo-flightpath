## Rulings applied

1. **Inputs are `projectId`, never paths.** Every contract input extends `{ projectId }`. The
   server resolves the root per call with
   `openProjectStore(projectDirectoryFromPaseo(context.paseo), projectId, { log })`. The client
   takes `projectId` from `useWorkspace(workspaceId, (w) => w.projectId)`. No `storeRoot` field
   exists anywhere in `shared/rpc.ts`.
2. **Errors travel as data.** The SDK `handle()` contract carries no typed error channel, so every
   output is `Result<T> = { ok: true; value: T } | { ok: false; error: RpcError }`, with
   `RpcError = { code: ErrorCode | "internal"; message: string; details?: unknown }`. Handlers
   never throw on purpose; unknown errors become `internal` and go to `console.error`.
3. **One graph model.** RPC commands call the core graph functions inside `store.transact`. The
   new pure commands Stage 1 needs (`insertQuestion`, `skipQuestion`) are added to
   `shared/graph.ts` beside the existing ones and follow the same `GraphChange` conventions. No
   second graph or status model exists on the server or in the client.
4. **UI writes are human writes.** The RPC service hardcodes `source: "ui"`,
   `actor: { kind: "human" }`. Agents write only through the Stage 2 MCP tools.
5. **Logging.** `PluginServerContext` 0.12.0 has no logger object. The paseo-plugin skill says
   the daemon captures plugin stdout/stderr into `paseo plugin logs`. So "plugin logger" means an
   injected `log` function, defaulting to `console.error`.
6. **TanStack Query lifecycle: host-owned cache.** The paseo-plugin skill (SKILL.md:640) says
   "The selected host owns the bundle, SDK calls, RPCs, and query cache", and the installed
   excalidraw panel calls `useQuery`/`useQueryClient` without mounting a provider. So the plugin
   mounts **no** `QueryClientProvider` and creates no `QueryClient`. Hooks use the host's
   `useQueryClient()`. Keys are additionally host-qualified as
   `["decision-roadmap", hostId, projectId, …]`, with `hostId` taken from
   `PluginHostProps.host.id`. Two daemons with the same `projectId` therefore never share
   entries, even if a host cache were shared. Dependency: `@tanstack/react-query@^5.90.11` (the
   excalidraw range).

### P1.1 Core hardening (Kimi Stage 0 notes)

- **H1 uniqueness.** In `shared/graph.ts` add, and call first inside `validateGraph`:
  ```ts
  export function assertUniqueIds(sessions: Session[]): void
  // invalid_input, details { duplicate: "session" | "question", id, sessionId? }
  ```
  It rejects a session id that appears twice and a question id that appears twice in one session.
  Because `store.read()` and `store.transact()` already call `validateGraph`, a store with
  duplicates is reported as `invalid` on import and a draft that creates one is rejected. In
  `server/store.ts` read validation, also reject duplicate `meta.links[].id` the same way.
- **H2 cycle guards (three-colour, diamond-safe).** The recursive memoised walks
  `computeVisibility` and `layoutDepth` use white/grey/black states:
  ```ts
  const state = new Map<RefKey, "grey" | "black">();   // absent = white
  // enter(key): if state.get(key) === "black" return memo.get(key)!   (shared descendant: reuse, no error)
  //             if state.get(key) === "grey" throw new DomainError("relation_cycle", `cycle at ${key}`, { at: key })
  //             state.set(key, "grey"); …recurse into parents…; memo.set(key, v); state.set(key, "black")
  ```
  Only re-entering a node that is still on the current recursion path (grey) is a cycle. A node
  reached a second time through another branch (a diamond) is black and reuses its memo value.
  `invalidationClosure` stays the current BFS with its `seen` set: it already terminates on any
  input and visits a diamond's shared descendant once. It gets no cycle detection of its own,
  because the command precondition below covers it. This holds even if the caller skipped
  `validateGraph`. Each exported graph command (`applyAnswer`,
  `confirmAnswer`, `updateDefinition`, `addRelation`, `removeRelation`, `insertQuestion`,
  `skipQuestion`) calls `validateGraph(sessions)` on its input first. Document this in a
  one-line comment: "inputs must be a valid graph; enforced".
- **H3 logging.** `StoreOptions.log?: (message: string, error?: unknown) => void`, default
  `(m, e) => console.error(m, e)`. The three `console.warn` prune calls use `log`.
  `openProjectStore` passes `opts.log` through (it already spreads `opts`).
- **New pure commands** in `shared/graph.ts`:
  ```ts
  export type QuestionDraft = Pick<Question, "title" | "context" | "options" | "allowFreeText"> & {
    recommendedOptionId?: string; activatedBy: Activation[]; invalidatedBy: Invalidation[];
  };
  export function insertQuestion(sessions: Session[], sessionId: string, id: string, draft: QuestionDraft):
    GraphChange & { questionId: string };
  // order = max(order)+1; definitionRev 1; validity "unanswered"; revisions/discussion [];
  // Question schema parse (invalid_input); not_found for session; then validateGraph
  // (unresolved_ref / relation_cycle). staleMarked [], visibilityChanged [].
  export function skipQuestion(sessions: Session[], ref: Ref, at: string): GraphChange;
  // requires active (question_inactive); validity "skipped", stale cleared, answer kept;
  // no stale propagation; visibilityChanged reports children deactivated because their
  // parent is no longer "valid".
  ```

```ts

export function buildOverview(data: RoadmapData, revision: number, disabled: boolean): Overview;
export function buildSessionView(data: RoadmapData, revision: number, sessionId: string): SessionView; // not_found
// questions sorted by `question.order`; catalog = every question of every session in document order;
// links = meta.links whose from/to sessionId equals sessionId.

// server/sessions.ts
export interface RoadmapServiceDeps {
  directory: (paseo: PaseoApi) => ProjectDirectory;   // default projectDirectoryFromPaseo
  now?: () => Date; newId?: () => string;              // default ulid()
  storeOptions?: Omit<StoreOptions, "storeRoot" | "projectId">;  // includes log, fs (tests)
}
export interface RoadmapService {
  version(paseo: PaseoApi, i: RpcInput<typeof RoadmapVersion>): Promise<Result<…>>;
  // …one method per contract, same name as the contract const in camelCase:
  // init, overview, sessionGet, sessionCreate, questionCreate, questionUpdate, questionAnswer,
  // questionConfirm, questionSkip, questionDiscuss, relationAdd, relationRemove, linkCreate, linkDelete
}
export function createRoadmapService(deps: RoadmapServiceDeps): RoadmapService;
```

Behaviour:
- Each method runs `openProjectStore(deps.directory(paseo), input.projectId, deps.storeOptions)`,
  then performs exactly one `read()` (queries) or one `transact(input.expectedRevision, draft => …)`
  (mutations). It wraps the body in `toResult`: `DomainError` becomes `{ ok:false, error:{code,message,details} }`
  and any other error is logged through `storeOptions.log` and becomes `internal`.
- Queries: `missing` → `store_missing`; `invalid` → `store_invalid` with `details: error`.
  `version` never fails on a missing or invalid store: it reports `status`.
- Mutations run inside `transact`, assigning `draft.sessions = change.sessions` from the core
  command. Ids come from `newId()`. `at` is `now().toISOString()`.
  - `sessionCreate` pushes `{ id, title, createdAt, status: "active", questions: [] }`.
  - `questionCreate` → `insertQuestion`. `questionUpdate` → `updateDefinition`.
  - `questionAnswer` → `applyAnswer` with `source "ui"`, `actor {kind:"human"}`.
  - `questionConfirm` → `confirmAnswer`. `questionSkip` → `skipQuestion`.
  - `questionDiscuss` appends `Note { id, at, actor: {kind:"human"}, text }` to the found
    question (via `findQuestion` on the draft) and changes no status.
  - `relationAdd/Remove` → `addRelation/removeRelation`.
  - `linkCreate` checks that every LinkEnd resolves (`unresolved_ref`) and pushes to
    `draft.meta.links`. `linkDelete` removes it (`not_found`). Neither touches any question.
- The store re-validates the draft on commit, so a graph error inside `fn` leaves no write.
  `revision_conflict` comes from the store unchanged.

### T1.2 Core hardening (`shared/graph-hardening.test.ts`)

- Two sessions with the same id → `validateGraph` throws `invalid_input` with `duplicate: "session"`.
- The same question id twice in one session → `invalid_input` with `duplicate: "question"`. The
  same question id in two different sessions is valid.
- A store whose generation contains duplicate question ids (written by hand) reads as `invalid`.
  Duplicate link ids also read as `invalid`.
- A hand-built activation cycle `a –act→ b –act→ a` (validation skipped): `computeVisibility`
  and `layoutDepth` each throw `relation_cycle`, with no stack overflow.
- A hand-built invalidation cycle `a –inv→ b –inv→ a`: `invalidationClosure(a)` terminates and
  returns `[b]`. `applyAnswer` on it throws `relation_cycle` through the precondition.
- **Diamond is not a cycle.** Setup (one session):
  - `x` is activated by `r∈{yes}` and invalidated by `r`.
  - `y` is invalidated by `r`.
  - `z` is activated by `x∈{yes}` and invalidated by both `x` and `y`.

  Expected:
  - `validateGraph` passes.
  - `layoutDepth` gives `{r:0,x:1,y:1,z:2}`.
  - `computeVisibility` returns four entries without throwing. `z` is active after `r=yes`,
    `x=yes`.
  - `invalidationClosure(r)` equals `[x, y, z]`, so `z` appears once.
  - With all four answered, changing `r` marks `x`, `y` and `z` stale, and `staleMarked` has
    length 3.
- An activation diamond across two sessions (`s1/r` → `s1/x`, `s2/y` → shared `s2/z`) passes
  `validateGraph` and reports the correct depths.
- `insertQuestion`: assigns `order` max+1, `definitionRev 1`, `unanswered`. An unknown activation
  parent gives `unresolved_ref`. A question activated by an existing one is inactive until its
  parent has the matching answer. The input array is unchanged.
- `skipQuestion`: sets validity `skipped` and keeps the answer. A child activated by that parent
  becomes inactive, reported in `visibilityChanged`. Nothing is marked stale. Skipping an
  inactive question → `question_inactive`.
- Store prune failure: a `faultFs` that fails `rm` makes the commit still succeed and the
  injected `log` receive a message containing `prune`.

  1. Create a session.
  2. Create `Q1(a,b)`, then `Q2` activated by `Q1∈{b}`. `Q2` is inactive.
  3. Answer `Q1=a`: rev 1, and `Q2` stays inactive.

  7. Answer `Q1=b` again (same value): no stale marks.
  8. Answer `Q1=a`: Q2 is now both inactive and stale.
