## Rulings applied (READY; derived from SPEC, plan and evidence; no new product behaviour)

1. **Canonical data.** Intents and mappings live only in the existing `Plan.intents` and
   `Plan.tickets` (SPEC §6), written through `store.transact`. There is no schema change and no
   migration: stores hold `[]`. The project scope is the Stage 2/3 `projectId → registered root`
   contract.
2. **Exact approved revision.** Preview and apply require `currency(...).status === "current"`
   for the plan's latest revision (SPEC §6 "rechecked … in `tracker.preview`/`tracker.apply`").
   Every action and intent references `{ planRev, taskId }` of that revision and the
   `receiptId` of its verified plugin-data receipt. If the plan is not current →
   `tracker_not_current` with the currency reasons.
3. **Actions (SPEC §7, plan 4.1).**
   - `create`: a task of the approved revision with no `TicketMapping` and no `TrackerIntent`
     in state `pending | sent | unknown` for its idempotency key.
   - `close`: a task whose `TaskState` for that revision is `verified` and whose mapping is
     `created`, when `closeByProject[projectKey]` is configured (O3, P4.6). Otherwise it is
     `skip("close not configured for <projectKey>")`.
   - `skip` with a reason: everything else, with `actionId: null`.
   - Idempotency key: `dr:<projectId>:<planId>:<planRev>:<taskId>:<kind>`.
   - The **actionable batch** is all `create` (and, after O3, `close`) actions of one preview.
     Apply confirms that entire batch; there is no subset selection.
4. **Exact payloads are wire payloads.**
   - The token signs exactly what would be sent.
   - In READY scope (dry-run, or live without an adapter) the payload is the provider-neutral
     `CreatePayload { title, body }`, labelled "provider-neutral (dry-run)". Here
     `body = task.description + "\n\n" + marker` and
     `marker = "decision-roadmap intent " + intentId + " (" + idempotencyKey + ")"`.
   - A live adapter (P4.6) supplies `render(action) → WirePayload`, the provider's
     exact request arguments. That rendered object is what the preview displays, the token
     signs, and the adapter sends unchanged. No field is added after signing.
5. **Stateless action ids and integrity binding.**
   - `actionId = base64url(canonicalJson({ v: 1, intentId, taskId, kind, planRev }))`, with
     `intentId` a ULID pre-allocated at preview.
   - `decodeActionId` parses it with a strict Zod schema (`v === 1`; ids match
     `/^[A-Za-z0-9_-]{1,128}$/`; `kind ∈ {"create"}`, plus `"close"` after O3), else
     `invalid_input`.
   - Apply rejects with `tracker_token_mismatch`:
     - duplicate `actionId`s or `intentId`s, or two actions for one `(taskId, kind)`;
     - a decoded `planRev` ≠ the latest revision;
     - a set of decoded actions that is not **exactly** the actionable batch the server rebuilds
       from the fresh plan and settings using those `intentId`s (missing, extra, swapped task or
       kind).
   - `confirmToken = base64url(HMAC-SHA256(trackerKey, canonicalJson(binding)))`, where
     ```
     binding = { v: 1, projectId, planId, planRev, contentHash, receiptId, destination,
                 settingsDigest: sha256Hex(canonicalJson(settings)), mode, storeRevision,
                 actions: [{ actionId, kind, taskId, intentId, idempotencyKey, payload }] /* sorted by actionId */ }
     ```
   - `trackerKey`: 32 random bytes published once with `publishNoClobber` at
     `<stateDir>/tracker-key.json` (0600, directories 0700, `fsync`).
   - Apply rebuilds `binding` from fresh state and compares with `tokensEqual`. Any drift in the
     store revision, receipt, plan hash, destination, settings (including future close config),
     mode or payload → `tracker_token_mismatch`.
6. **Durable intent before any remote call, rechecked per action (plan 4.1).**
   - Live apply processes the batch sequentially and keeps its own `batchRevision`, starting at
     `expectedRevision`.
   - For **each** action:
     1. Read settings fresh. Then, in `transact(batchRevision)`, recheck: latest `planRev` and
        `contentHash` equal the binding; `currency` is `current` (verified receipt plus
        `basisCurrent`); `settingsDigest` and `destination` are unchanged; no conflicting intent
        exists. Then append `TrackerIntent { state: "pending", payload, … }`. Set
        `batchRevision` to the returned revision.
     2. `transact(batchRevision)` sets `sent` and `lastAttemptAt`, then sets `batchRevision`.
     3. Run the adapter call, under a `timeoutMs` race.
     4. Record the outcome:
        - a confirmed response writes the mapping and sets the intent to `confirmed`;
        - `TrackerError("definitive")` sets `failed`, with a redacted error code;
        - a timeout, network error, 5xx or unclassified error sets `unknown`.

        The outcome is recorded by `transact(batchRevision)`. If that conflicts because of a
        foreign write, the outcome is still recorded with up to 3 retries at the latest revision.
        It modifies only this intent and its mapping, so a rebase is safe. The batch is then
        **stopped**.
   - Steps 1–2 failing their recheck or hitting `revision_conflict` → stop. The current action
     reports `not_attempted` (error `intent_not_sent` if its `pending` was persisted), and the
     remaining actions report `not_attempted`, with no adapter call.
   - If recording fails after all retries, the intent stays durably `sent`. The result is
     `unknown` with error `"outcome not recorded"` and, for information only, the returned
     remote key. It **does not claim** a mapping.
   - `unknown` is never retried automatically and blocks new intents for that key.
7. **No blind duplicate.**
   - `tracker.reconcile` performs **no remote lookup**. Contract 3 found no idempotency
     guarantee, and the plan allows a lookup only if one is verified.
   - It returns the intent's state, and for `pending | sent | unknown` it returns
     `humanDecisionRequired: true`.
   - Intents left in `pending` or `sent` with `lastAttemptAt` before plugin start (or created
     before start, for `pending`) are reported as `interrupted` in preview. Their tasks are
     skipped "needs reconcile" and are never re-sent.
   - How a human resolves them is **P4.7 (O2)**: link a manually found ticket, or confirm explicitly that none was created.
8. **Modes and defaults (SPEC §9).** Settings default to `{ provider: "none", mode: "dry-run" }`.
   - `provider: "none"` → every action is `skip("provider none")`.
   - `dry-run` → apply validates the token and returns `state: "dry_run"` per action. It
     **persists no intent or mapping and calls no adapter write method** (asserted with a
     recording adapter).
   - `live` → apply uses the adapter from `adapterFor(settings)`. While O1 is unresolved there
     is **no live adapter**: it returns `tracker_unavailable` without persisting intents.
9. **Owner confirmation channel.** `tracker.apply` is a plugin RPC called from the preview
   modal, and the commands refuse non-UI origins. There is **no MCP tracker tool** (SPEC §8).
   The Stage 3 honesty note applies: the server cannot prove which human pressed Apply.
10. **New error codes.** `tracker_not_current`, `tracker_token_mismatch`,
    `tracker_unavailable`, `tracker_intent_unresolved`. They are added to `ErrorCode` and
    `RPC_ERROR_CODES`, enforced by the existing sync check.
11. **Redaction.** Logs carry the intent fingerprint (`sha256(intentId)[:8]`), action kind and
    state only. Never payload bodies, credentials or remote error bodies (only the error
    class).

- **`preview`**:
  - Non-UI origin → `invalid_input`.
  - Read the store and compute `currency` (reusing the Stage 3 verified-receipt logic; extract a
    shared helper inside `server/plans.ts` only if needed, exported without behaviour change).
    Not current → `tracker_not_current`.
  - Build actions per rulings 3–4 with fresh `intentId`s and encode the `actionId`s
    (ruling 5).
  - Compute `binding` and the token, then report `interrupted` (ruling 7).
- **`apply`**:
  - Non-UI origin → `invalid_input`.
  - Decode and validate every `actionId` (ruling 5).
  - Rebuild the actionable batch from the fresh plan and settings with exactly those
    `intentId`s, then rebuild `binding` with `storeRevision = expectedRevision`.
  - **Error precedence** (confirmed by coordinator and tester; supersedes the earlier blanket
    drift wording). Checks run in this order:
    1. non-UI origin → `invalid_input`;
    2. a malformed `actionId` → `invalid_input`;
    3. current store revision ≠ `expectedRevision` → `revision_conflict`;
    4. the revision is fresh but the latest plan is not `current` → `tracker_not_current`
       (ruling 2);
    5. the plan is current but the rebuilt batch or `binding` differs (subset, swapped or extra
       ids, settings, mode, destination or payload drift) → `tracker_token_mismatch`.
  - `dry-run` → return `dry_run` results with no writes.
  - `live` with a null adapter → `tracker_unavailable` with no writes.
  - Otherwise run the ruling 6 per-action loop.
- **`reconcile`**: read-only (ruling 7). An unknown intent → `not_found`.
- Store access goes through the `StoreOpener`. Tests inject failures through a wrapping `Store`
  (no new production port).

### P4.8 Read-only tracker list and plan-view integration (READY; closes the P4.5 list gap)

Evidence (coordinator, `af46559` on `2f1ec4c`):
- `PlanView.plan` omits `intents` and `tickets` (`shared/rpc.ts:222-224`), and `plans.get`
  strips them.
- `tracker.preview` requires a current approval and lists no mappings.
- `tracker.reconcile` needs a known `intentId`.

So the approved persistent list cannot be supplied. A separate read RPC fills the gap without
changing the frozen Stage 3 `PlanGet`, its MCP status tool or the 13 MCP tools.

```ts
// server/tracker/list.ts
export function listTracker(open: StoreOpener, i: RpcInput<typeof TrackerList>, deps: { processStartedAt: Date }):
  Promise<Result<ValueOf<typeof TrackerList>>>;
// TrackerService gains: list: (paseo, input) => … (live opener; no origin needed: read-only)
```
- **Inputs and resolution:** `{ projectId, planId }`, opened through the normal canonical opener
  (`projectId → registered root`). One `store.read()`. `missing` → `store_missing`, `invalid`
  → `store_invalid`, unknown plan → `not_found`.
- **Independent of approval and settings:** it does not call `currency`, read settings, call
  the adapter (`render`, `send` or `get`), run `transact` or `syncExport`, or touch the tracker
  key.
- **Tickets:** every `plan.tickets` entry. `taskId`/`planRev` are joined from the intent with
  the same `intentId` (`null` if that intent is absent).
- **Intents:** every `plan.intents` entry whose state is not `confirmed` (confirmed ones are
  represented by tickets).
  - `interrupted` is true for `pending`/`sent` intents with `lastAttemptAt` before

`server/tracker/resolve.ts`:
`resolveIntent(open, input, origin, deps: { live, processStartedAt, audit: AuditStore, now, log })`.

- **Guards (in order):**
  1. non-UI origin → `invalid_input`;
  2. store revision ≠ `expectedRevision` → `revision_conflict`;
  3. the intent is missing → `not_found`;
