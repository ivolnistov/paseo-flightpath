### 1.2 Grilling completion (pure, `server/plan-rules.ts`, P, in R2.1)

```ts
export function grillingComplete(sessions: Session[], sessionId: string | undefined, cancelled: ReadonlySet<RefKey> = new Set()): boolean
```

It receives **all** sessions, because visibility is computed over the full graph: a question of
the grilling session may be activated or deactivated by a question in another session. `true` iff
`sessionId` names an existing session, `basedOnSnapshot(sessions, [sessionId], cancelled)` (the
shipped full-graph active-question snapshot, cancelled refs excluded) is non-empty, and every
entry has validity `"valid"` (answered and not stale). `skipped`,
`unanswered` and `stale` all make it incomplete. Block acceptance is not required: a session with
blocks always has one open block (model invariant), so requiring it could never hold. This is the
technical definition chosen for "grilling completes" (design §4, Q27=1); see §6 **G1**.

### 2.2 Interfaces (exact)

```ts
export type BlockerContext = { features: Feature[]; sessions: Session[]; cancelled: ReadonlySet<RefKey> };
export function approvalBlockers(plan: Plan, ctx: BlockerContext): ApprovalBlocker[]
```

For the latest revision `latest` of `plan`:

1. No revision → `[]`.
2. `latest` without `schema` (legacy revision): `[]` when the plan is unbound (legacy rules
   exactly as shipped); `[{ code: "legacy_revision" }]` when the plan is bound (defensive; R1.0
   drafting cannot produce it).
3. `latest` with `schema: 2`, in this order, every applicable blocker (no early return):
   - per task in task order with `dod.trim() === ""` → `{ code: "dod_missing", taskId }`;
   - feature grilling, only for a bound plan and unless the feature's `kind === "bug"`
     (design §4: bug grilling optional): not `grillingComplete(sessions, feature.grillSessionId, cancelled)` →
     `{ code: "grilling_required", sessionId?: feature.grillSessionId }` (no `taskId`);
   - plan grilling: not `grillingComplete(sessions, plan.grillSessionId, cancelled)` →
     `{ code: "grilling_required", sessionId?: plan.grillSessionId }`;
   - per task in task order with `grill === true`: not
     `grillingComplete(sessions, task.grillSessionId, cancelled)` →
     `{ code: "grilling_required", taskId, sessionId?: task.grillSessionId }`.
   - `sessionId` is present exactly when the link exists, even if that session no longer exists.
   - A bound plan whose feature record is missing (impossible after R1: `feature.delete`
     refuses a bound feature) → `DomainError("not_found", …, { featureId })`.
   - An unbound plan with a `schema: 2` latest revision cannot be produced by drafting (R1.0
     binds on the first v2 draft) but exists in shipped test fixtures written directly to the
     store; it gets the DoD, plan and task gates and no feature gate, so it stays fail-closed.

`gates_not_available` is never produced again. The enum value stays in `ApprovalBlocker` (shape
unchanged, plan R2.1) so old clients and fixtures still parse.

### 2.3 Callers

- `plan.get`: `blockers: approvalBlockers(plan, { features: read.data.features, sessions: read.data.sessions, cancelled: cancelledRefs(read.data) })`.
- `plan.approve`: same call, same position (after the rev check, before the content hash check);
  non-empty → `DomainError("plan_ineligible", "the revision cannot be approved yet", { blockers })`.
  The message changes; the code, `details.blockers` and precedence do not.
- `plan.approve` of a bound `schema: 2` revision, after the receipt is written, moves the feature
  `created → planned` with a `status` event `{ from: "created", to: "planned", reason: "plan approved" }`
  inside the same retried copy transaction that records the receipt copy (design §3.1, §3.6 row
  "Approve revision (feature created)"). A feature in any other status is unchanged (row
  "feature deferred" keeps `deferred`). If the copy transaction cannot commit, the receipt stays
  authoritative and the status write is retried by the next `plan.approve` of the same revision
  (`alreadyApproved: true` path runs the same transaction). See §6 **G4**.

### 3.2 Behaviour (exact)

Inside the `plan.draft` transaction of a **bound** draft (`featureId` present), after eligibility
and binding checks and before hashing:

1. Feature session: if `feature.kind === "feature"` and `feature.grillSessionId` is undefined,
   create `{ id: newId(), title: "[feature] " + feature.title, createdAt: at, status: "active", questions: [] }`
   in `draft.sessions` and set `feature.grillSessionId`. A bug gets no automatic session.
2. Plan session: if `plan.grillSessionId` is undefined, create `"[plan] " + i.title` the same way
   and set it.
3. Task sessions, per task of the new revision:
   - `grill === true` and the latest existing revision has a task with the same id whose
     `grillSessionId` is set → copy that id (carry-over, C7 ruling);
   - `grill === true` otherwise → create `"[task:" + task.id + "] " + task.title` and set it;
   - `grill === false` → no `grillSessionId` (link dropped; the session stays in the store).
4. `grillSessionId` is then part of the task object and of `contentHashV2` (shipped hashing).
5. Grilling sessions are **not** added to `plan.sessionIds` and do not enter `basedOn`; the
   caller's `sessionIds` stay the plan basis (§6 **G2**).
6. Legacy drafts create nothing. `TaskInput` still rejects `grillSessionId` (strict, R1.0).
7. Feature and plan sessions are created at most once per feature and per plan; a re-draft
   reuses them.

New sessions are ordinary empty sessions: they convert to blocks on their first block-scoped
question exactly as today.

MCP `roadmap_dod_template` (new, read-only): input `{}`; output `{ source, text }` from the same
resolver as `dod.template.get` (file > project > global, Q31=1); description states that the
template is guidance for the agent's tailored DoD proposal (Q28=3) and is never applied by itself.
Contract versus table: R2.2 defines the tool in `buildPlanTools(plan, dodTemplate?)`, where
`dodTemplate?: (projectId: string) => Promise<Result<{ source; text }>>`; the tool is listed only
when the resolver is passed. R2.4 (integration) passes the resolver in `index.server.ts`
(`buildPlanTools(planCommands, dodTemplate)`), which makes the tool live; `server/mcp-tools.ts`
is unchanged (c0008).

R2.2 also updates the R2.1 expectations that include grilling blockers (§2.5 rows
`plans.test.ts:681-690` and `:863-874`): bound drafts now create links, so the feature and plan
blockers carry the created `sessionId`, and `grilling_required t2` carries its task session id.

### 3.3 Test contract (T writes RED first)

- First bound draft of a feature-kind feature creates exactly one `[feature]` and one `[plan]`
  session and links them; a second draft creates none; a bug feature gets only the `[plan]`
  session.
- `grill: true` creates `[task:<id>]` and sets `grillSessionId`; redraft with `grill: true`
  carries the same id; redraft with `grill: false` drops it and the session remains in the
  store; flipping back to `true` creates a new session (no resurrection of a dropped link).
- Client-supplied `grillSessionId` → `invalid_input` (UI and MCP).
- Legacy draft: no session created; body and hash byte-identical to the shipped legacy draft.
- `roadmap_dod_template` returns the same `{ source, text }` as `dod.template.get` for file,
  project, global and none.
- RED control: at the R2.1 commit the session cases fail; legacy cases pass.

### 4.2 Interfaces (exact)

```ts
export const PlanRework = defineRpc({
  name: "plan.rework",
  input: Mutation.extend({ planId: Id, planRev: z.number().int().min(1), reason: z.string().trim().min(1).max(2000) }),
  output: result(Written),
});
```

UI only (`origin.source === "ui"`, otherwise `invalid_input` "rework only in the Paseo UI"); no MCP
tool. In one transaction:

1. The plan is bound; `planRev` is its latest revision; that revision has a verified receipt
   (approved) and is not already in `reworks`; the feature status is `planned` or `executing`.
   Otherwise `invalid_input` (unbound, already reworked, wrong status) or
   `plan_revision_mismatch` (not latest).
2. Append `reworks: { planRev, at, reason, actor: { kind: "human" } }`.
3. The revision's task set is cancelled (design §3.2, §3.6 "cancelled, work and completion record
   kept"): every task of that revision that is not `verified` gets `status: "cancelled"`
   (existing state replaced, missing state added). A `verified` task's state, including its
   `verification` note, is left exactly as stored: it is the completion record, not a live task,
   because the revision is superseded and no transition leaves `verified`. It becomes a reuse
   candidate only; nothing is carried into a new revision, which materialises its own task
   states from `todo` (design §3.2: "never carried over automatically because text or ids
   match"). Old revision objects, hashes and receipts are untouched.
4. Feature → `created`, `statusReason: "plan in rework"`, status event with that reason (Q25=1).
   Runs are R3; this stage has no run to end.

Effects elsewhere:

- `currency` of a superseded latest revision → `{ status: "not_current", reasons: ["revision <rev> was sent for rework"] }`
  before receipt checks, so `task.update` (`plan_not_current` on start), tracker apply
  (`tracker_not_current`) and `roadmap_plan_status` all follow.
- `plan.approve` of a superseded revision → `plan_not_current` with the same reason.
- `plan.get` gains `reuseCandidates?: Array<{ planRev, taskId, title, verifiedAt? }>` (optional in
  `PlanView`, present only when non-empty, so older clients and fixtures still parse): the
  `verified` task states of every superseded revision of the plan, newest revision first; never
  applied automatically. `verifiedAt` is optional and copied only from an existing
  `state.verification.at`; a historical `verified` state without a verification record is still a
  candidate, without a date (no invented timestamp, no tightening).
- The next bound draft creates `rev + 1`; its approval materialises its own tasks
  (states start at `todo` lazily as today) and moves the feature `created → planned` (R2.1).
  `statusReason` is cleared on that transition.
- `taskTransition`: any move to or from `cancelled` → `task_transition`. In the same commit the
  `task.update` input becomes `TaskState.shape.status.exclude(["cancelled"])` (UI `verified`
  with a note stays, §6 **G3**); `roadmap_task_update` stays `in_progress | done`.
- `client/plan-view.tsx` lists `reuseCandidates` under the task preview as read-only text
  ("Completed in revision N: <title>", followed by the date only when `verifiedAt` is present)
  when non-empty. No Rework control in R2 (the stop-and-rework
  control is R4.2, run controls).

### 4.3 Test contract (T writes RED first)

- Rework of an approved latest bound revision: `reworks` entry, task states `cancelled` except
  `verified` ones, feature `created` with reason "plan in rework" and one event; old revision
  objects, receipts and hashes byte-identical.
- Refusals: MCP origin; unbound plan; unapproved revision; not latest; already reworked; feature
  `created`, `done`, `deferred` or `cancelled`.

- Re-draft and approval: new revision approves (gates satisfied), feature `planned`,
  `statusReason` cleared, new task states independent of the old revision's.
- `task.update` to `cancelled` rejected at RPC (schema) and MCP (schema); from `cancelled` →
  `task_transition`.
- Client: `PlanView` renders the reuse list when present and nothing when empty.
- RED control: at the R2.2 commit every rework case fails (no contract); legacy plan cases pass.

## 6. Plan inconsistencies and gaps (settled here or reported)

- **G1 (labelled default, revisable): what "grilling completes" means.** The owner was shown
  this question with option 1 recommended and then gave the explicit proceed goal "commit r2 r3
  r4 and merge in master with working tests, lints, e2e tests and kensai-local checks" (coordinator
  ruling, 2026-10-28). Option 1 is applied as a labelled default; it is not an answer to the
  question. Neither the design nor the plan defines it.
  This card chooses §1.2 (≥ 1 active non-cancelled question, every one answered and not stale;
  skipped is not complete; block acceptance not required). Alternatives: also accept `skipped`;
  or require the session's last block to be accepted (would need an explicit "finish grilling"
  action, since one block is always open).
- **G2 (labelled default, revisable): do grilling sessions join the plan basis?** Shown with
  option 1 (link sessions only, not the basis) recommended, followed by the same explicit owner
  proceed goal; option 1 is applied as a labelled default, not an answer. The plan says sessions are "linked
  by id" and nothing more. This card keeps them out of `sessionIds`/`basedOn` (the drafter keeps
  choosing the basis). Including them would make every grilling answer invalidate the approval
  basis and force a re-draft after grilling.
- **G3 (settled, plan wording conflict):** plan §1 narrows `task.update` to `todo | in_progress |
  done`, but the shipped UI verification of legacy plans uses `task.update` with `verified` and a
  note (global constraint: preserve shipped behaviour). This card removes only `cancelled` from
  the input and keeps `verified` for the UI; MCP was already `in_progress | done`.
- **G4 (settled, design-mandated gap):** no R2 task names the `created → planned` transition on
  approval (design §3.1, §3.6), yet R3 readiness needs `planned`. R2.1 adds it in the approval
  copy transaction.
- **G5 (settled, file-list gap):** "reuse candidates in the preview" needs a client display, and
  R2 lists no client file. R2.3 adds a read-only list in `client/plan-view.tsx`; no new control.
- **G6 (settled):** "superseded" storage is a plan-level `reworks` list, so frozen revision
  objects and hashes are never edited.
- Not in R2: runs, stop-and-rework UI control, run end on rework (R3.5, R4.2).

### 8.2 c0011: one plan per feature (shared producer)

In `draftBinding(data, plan, i)` (`server/plans.ts`), after the existing checks, when the draft
would bind (a new plan with `featureId`, or an existing unbound legacy plan given `featureId`) or
redrafts a bound plan:

```ts
const others = data.plans.filter((p) => p.featureId === i.featureId && p.id !== plan?.id);
```

- binding draft (no `plan` or `plan.featureId === undefined`) and `others.length >= 1` →
  `DomainError("invalid_input", "the feature already has a plan; draft a new revision of it",
  { reason: "feature_has_plan", featureId, planId: others[0].id })`;
- redraft of a bound plan and `others.length >= 1` (old duplicate data) →
  `DomainError("invalid_input", "the feature has more than one plan", { reason:
  "feature_has_multiple_plans", featureId, planIds: [plan.id, ...others.map((p) => p.id)].sort() })`;
- ordinary redrafts of a feature's single bound plan are unchanged. RPC and MCP inherit it (same
  producer). The guard runs before any session is created, so a refused draft creates nothing.

Duplicate data stays readable (`feature.list`, `plan.list`, `plan.get` unchanged). Writes fail
closed with no side effect, using a shared helper `boundPlans(data, featureId): Plan[]`:

- `plan.approve`: for a bound plan whose feature binds more than one plan, after the revision
  check and before blockers, content hash, basis and `approvals.write` →
  `invalid_input { reason: "feature_has_multiple_plans", featureId, planIds }`.
- `plan.rework`: the same check inside its transaction, before any change.

### 8.3 c0004: `statusReason` describes the current status only

`feature.status.set` (`server/features.ts`): on every manual change (cancel, defer, undefer)
`delete feature.statusReason` first. Undefer restores `statusBeforeDefer` and then re-derives:
`statusReason = "plan in rework"` iff the restored status is `created` and the feature's bound
plan's latest revision is in `Plan.reworks`; otherwise none. With duplicate bound plans the
re-derivation uses any bound plan whose latest revision is reworked (read only; no write fails).
Status events and `Plan.reworks` are unchanged; `plan.rework` still sets the reason and the
approval copy still clears it. Screens keep showing `statusReason` when present.

### 8.4 c0015: approval effects pending (derived)

`shared/rpc.ts`: `PlanView.approvalEffectsPending?: Array<{ effect: "project_copy" |
"feature_planned"; reason: string; retryBlocked?: "feature_has_multiple_plans" }>`, strict
entries, absent when empty. `retryBlocked` is additive, optional and derived; it names an
already-defined server refusal (coordinator technical ruling, §8.6).

`plan.get` (`server/plans.ts`) derives it from the verified receipt of the latest revision
(none → absent):

- `project_copy` when `plan.approvals` has no copy with that `receiptId` (reason "the project copy
  of approval <receiptId> is not recorded");
- `feature_planned` when the plan is bound, its feature exists with status `created`, and the
  approved revision is the latest, schema 2 and not reworked, with `rev`, `contentHash` and
  `decisionSnapshotHash` equal to the receipt (the copy transaction's `approvedIsLatest`
  conditions) (reason "the feature is still created"). Deferred, cancelled, planned, executing
  and done features never report it.
- When the feature binds more than one plan, no `feature_planned` is reported, and every pending
  entry (here `project_copy`) carries `retryBlocked: "feature_has_multiple_plans"` with the reason
  "approval effects cannot be retried while the feature has more than one plan".

`client/plan-view.tsx`: when `approvalEffectsPending` is non-empty, show each reason under the
Approve area. Show an `ActionButton` "Retry approval effects" that calls the existing UI
`plan.approve { rev, contentHash }` of the displayed revision only when all hold: the displayed
revision is the latest; it is not in `plan.reworks`; `blockers` is empty; `approval === "current"`; and no entry
has `retryBlocked`. Eligibility never reads the reason text. Otherwise the reasons are shown and there is no control;
the line "The approval gates now block this; resolve them first." is added only when `blockers` is
non-empty and no entry has `retryBlocked` (c0036, §8.8). On success the view refetches;
`plan.approve` re-checks everything before `approvals.write` and the copy, so the control never
bypasses a gate.
