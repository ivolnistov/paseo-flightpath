### 2.1 Persistence invariants (normative for all of R0)

- I1 No Zod `.default()`, `.transform()`, `.catch()` or preprocessing on any persisted schema
  (everything reachable from `RoadmapDataV1`, `RoadmapDataV2`, `Feature`, `ExecutionRun`,
  `StartDelegation`). For every valid input `x`, `canonicalJson(Schema.parse(x)) ===
  canonicalJson(x)`. Defaults belong to RPC/MCP input contracts only.
- I2 Strict legacy v1: `RoadmapDataV1` accepts exactly what the shipped `RoadmapData` accepts at
  `feb6905` and nothing more. A v1 generation containing any v2-only field (`schema` on a
  revision, `featureId` on a plan, `blocks` on a session, `blockId` on a question, v1 meta with
  v2 keys) is rejected.
- I3 Additive v2: every valid v1 session, question, plan and revision object is also a valid v2
  object unchanged (deep-equal after parse). v2 adds optional fields and new record types only.
- I4 v1 hashing is frozen: `contentHash` (existing export, same signature) and
  `decisionSnapshotHash` produce byte-identical output to `feb6905` for every input.
- I5 Versioned hashing is total and domain-separated: `contentHashFor(rev)` uses the v1 function
  iff `rev.schema` is absent and the v2 function iff `rev.schema === 2`; a v2 hash never equals
  the v1 hash of the same four fields.
- I6 v1-only stores remain rejected by old plugins: `Manifest.version` stays `1`; a v2 generation
  has `roadmap.json` with `version: 2`, which the `feb6905` strict `RoadmapMeta` rejects as
  invalid (fail closed, never misread).
- I7 Legacy markers are derived, never stored: "legacy plan" = `plan.featureId === undefined`;
  "legacy revision" = `rev.schema === undefined`; "legacy blocks" = `session.blocks ===
  undefined`. No `legacy` or `legacyBlocks` field is ever persisted (see §9 item 1).

## 5. Task R0.4: grilling blocks and frozen-block rule

Files (P): `server/sessions.ts`, `shared/rpc-blocks.ts` (new). Files (T):
`server/sessions-blocks.test.ts` (new).

Interfaces:
- `BlockAccept = defineRpc({ name: "block.accept", input: { projectId, sessionId, blockId,
  expectedRevision }, output: result({ revision, blockId, nextBlockId }) })`.
- `QuestionCreateV2Input` (in `shared/rpc-blocks.ts`) = shipped `QuestionCreate` input +
  `blockId?: Id`; R0.6 points `QuestionCreate` at it.
- Commands: `blockAccept(open, input, origin)` UI origin only; `questionCreate` accepts
  `blockId`. Semantics: the first `question.create` with a `blockId` on a session without
  `blocks` converts it only if the session has no questions (a session with legacy questions
  keeps legacy semantics and rejects `blockId` with `invalid_input`); a session with blocks
  always has exactly one open block, the highest `order`; accepting it creates the next open
  block. Any direct mutation of a question in an accepted block (update, answer, confirm, skip,
  discuss, relation add/remove with it as target) → `DomainError("block_frozen")`. A relation
  whose target is an open question and whose parent or upstream is a frozen question is allowed:
  it is stored only on the open target (`activatedBy`/`invalidatedBy`), leaves the frozen
  question byte-identical, and matches `question.create` with the same dependency (plan R0.4,
  authoritative; R0 review c0001 restored this scope). Frozen means the
  question's content (answer and revisions, definition, discussion, own relations, `blockId`),
  not its derived validity: when an open upstream question is re-answered, the existing
  `applyAnswer` propagation may set `validity: "stale"` and `stale: { cause… }` on a frozen
  dependent, and that write succeeds (owner clarification 2026-10-26). The transaction-level
  frozen-state comparison therefore compares a content projection that omits `validity` and
  `stale`; everything else in the projection must stay byte-identical. Accepted `Block` records
  stay fully frozen.
- Legacy view (computed, never stored): `effectiveBlocks(session)` returns one synthetic block,
  `open` when the session is active, `accepted` when closed; legacy sessions are never frozen by
  this rule (closed sessions keep today's behaviour).
- Test contract: plan R0.4 bullet T, including: `relation.add`/`relation.remove` with a frozen
  target → `block_frozen`; with an open target and a frozen parent or upstream → success, frozen
  question byte-identical; plus a legacy fixture session's file bytes are unchanged after
  unrelated writes.
