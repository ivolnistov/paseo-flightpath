## Rulings applied (READY)

1. **No new persisted fields; no migration.** The Stage 0 `Plan` schema already holds
   `revisions`, `approvals` (copies), `taskStates`, `intents` and `tickets`. Stage 3 fills
   `revisions`, `approvals` and `taskStates` only. Existing stores contain `plans: []`, so no
   data migration is needed.
2. **Hashing on the server.** This follows Stage 0 ruling D1: `server/plan-hash.ts` uses
   `sha256Hex(canonicalJson(...))`, and `shared/` stays Node-free.
   - `contentHash = sha256Hex(canonicalJson({ markdown, tasks, basedOn, decisionSnapshotHash }))`
     (SPEC §6, exact key set).
   - `decisionSnapshotHash = sha256Hex(canonicalJson(basedOnSnapshot(sessions, sessionIds)))`.
     `basedOnSnapshot` lists **every currently active question** of the plan's `sessionIds`
     (the active branch, R2), sorted by `refKey`, each as
     `{ sessionId, questionId, answerRev, definitionRev, validity, value: { optionId?, text? } }`.
     The value is taken from the question's current answer.
   - Inactive questions are not in the snapshot, so edits on a hidden branch do not affect it.
     A branch change (a question entering or leaving the active set) or a new active question
     changes the active set, and therefore the hash.
   - `basedOn` holds the same active set, without `value`.
   - `sessionIds` for currency checks is `plan.sessionIds`, which every draft sets to the
     latest revision's sessions.
3. **Markdown export is derived state, and always renders the latest revision.**
   - File: `<storeRoot>/.decisions/plans/<planId>.md` with content
     `renderExport(planId, latest) = exportHeader(planId, latest.rev, latest.contentHash) + "\n\n" + latest.markdown + "\n"`.
   - `syncExport(store, planId)` never takes a revision argument. Under a per-`(storeRoot, planId)`
     in-process mutex it:
     1. reads the store;
     2. renders the **current latest** revision;
     3. compares the **complete** expected bytes with the file;
     4. writes (temp file plus `rename`; overwriting a derived file is intended) only on a
        difference;
     5. re-reads the store revision and, if it moved, repeats, at most 3 rounds.
   - A slow post-commit sync for an older draft therefore cannot leave older content: it
     renders whatever is latest when it holds the mutex. A body edited by hand under an intact
     header is detected and repaired, because the comparison covers the full content.
   - Called after draft and approve commits, and by `plan.get` (repair). The file is never
     parsed back. Failure leaves the commit intact and reports `exportWritten: false`. The file
     lives outside `generations/`, so prune never touches it.
4. **Receipts are server-owned and stored outside the project.**
   - Path: `<stateDir>/approvals/<projectId>/<planId>/<rev>.json`, where `stateDir` is
     `defaultStateDir()` and is injectable. Directory mode `0o700`, file mode `0o600`.
   - Publication is **atomic and no-clobber** through a dedicated port, `server/approval-fs.ts`.
     The frozen `StoreFs` is not changed: it has no mode, `chmod` or `link` operation, and its
     `writeFileDurable` uses `wx` without `0600`. POSIX `rename` replaces its destination, so
     it is not used for receipts.
     1. Write `open(tmp, "wx", 0o600)`, then write, `fsync`, close.
     2. Publish with `link(tmp, final)`, which fails with `EEXIST` when a receipt already exists.
     3. `unlink(tmp)`, then `fsync` the directory.

     A crash before `link` leaves only a `.<rev>.json.tmp-<id>` file, never a partial final
     file. Temp files older than 60 s in that directory are removed on the next publish. If
     `link` is unsupported (`EPERM`/`ENOTSUP`), the approval fails with `internal`; there is no
     clobbering fallback.
   - It is Zod-validated as `ApprovalReceipt`.
   - The project-JSON `plan.approvals` copy is only for readability. A copy with no matching
     plugin-data receipt, or a receipt whose `projectId`, `planId`, `planRev`, `contentHash` or
     `decisionSnapshotHash` differs from the plan revision, is reported `unverified` and never
     counts.
5. **Approval channel, stated honestly.** `plan.approve` exists only as a plugin RPC
   registered by `registerPlanHandlers` and is called from the Plan view. There is no MCP
   approve tool.
   - `PluginHandlerContext` 0.12.0 carries only `{ paseo }`
     (`@getpaseo/plugin/dist/server/contracts.d.ts:8-10`). So the server **cannot prove** that a
     human pressed the button, or which client did. The receipt records
     `actor: { kind: "human" }` meaning "UI RPC channel", and `hostClientId` is omitted.
   - The security property is narrower: agents reach the roadmap only through MCP grants (Stage 2),
     which have no approve path, and no file content is ever accepted as approval.
   - A local process able to call the plugin RPC or write plugin-data is outside this model
     (see the report).
6. **Approve is idempotent per revision and bound to the exact hash.** `plan.approve` takes
   `{ projectId, planId, rev, contentHash, note? }` and **no** `expectedRevision`: the
   `(rev, contentHash)` pair is the optimistic check.
   - **Precondition** (independent of receipt existence):
     - `rev` is the latest revision;
     - `contentHash` equals the stored hash and a fresh recomputation;
     - `basisCurrent(sessions, plan.sessionIds, revision).ok` holds, i.e. the recomputed
       `decisionSnapshotHash` equals the revision's and every basis entry is intact.

     It deliberately does **not** use `currency(...).status === "current"`, which needs a
     receipt and would block the first approval. `basisCurrent` includes the R1 rule: any
     basis entry with `validity: "skipped"` blocks approval (`plan_not_current`, reason
     `"<ref> is skipped; answer it and draft a new revision"`).
   - If a receipt for that `rev` already exists, it returns `{ alreadyApproved: true }` with
     that receipt (the no-clobber publish reports `exists` and the stored receipt is returned).
   - Order of operations:
     1. Read the store and check the precondition.
     2. Publish the receipt.
     3. Append the copy through `transact(currentRevision)`, retrying at most 3 times on
        `revision_conflict` (the copy is cosmetic).
     4. Run `syncExport`.

     The result includes `copyRecorded` and `exportWritten`. A receipt for a revision that a
     concurrent draft superseded between steps 1 and 2 is harmless: currency requires a receipt
     for the latest revision.
7. **Task state belongs to the approved revision, addressed exactly.** `TaskState` is keyed by
   `(planRev, taskId)`, and states never carry over (SPEC §6: "reference `{ planRev, taskId }`
   of the approved revision, never a mutable description").
   - Every task action carries `planRev` and `contentHash`, plus `expectedRevision`.
   - The server requires `planRev === latest.rev` and
     `contentHash === latest.contentHash`, otherwise `plan_revision_mismatch`. So an action
     taken from an older displayed revision is rejected even when the new revision reuses the
     task id and the client cache is fresh.
   - Transitions: `todo → in_progress → done → verified`, plus `in_progress → todo` and
     `done → in_progress`.
   - `in_progress` requires `approvalCurrent === "current"` for that latest revision. This is
     SPEC §6 "currency is rechecked at execution start".
   - `verified` requires a non-empty `verification.note` and the UI origin. MCP can move tasks
     only to `in_progress` or `done` (SPEC §8).
8. **New error codes.** `plan_revision_mismatch`, `plan_ineligible` (details:
   `{ refs: Ref[], reasons: string[] }`), `plan_not_current`, `task_transition`. They are added
   to `shared/errors.ts` `ErrorCode` and to `RPC_ERROR_CODES`; the existing compile-time sync
   check enforces both.
9. **Separate registration, no change to frozen contracts.** Plan RPCs live in
   `STAGE3_CONTRACTS`, registered by a new `registerPlanHandlers(server, planService, holder)`.
   `STAGE1_CONTRACTS`, `ROUTES`, `Overview` and their tests stay unchanged. Plan MCP tools are
   passed through `buildTools(commands, buildPlanTools(planCommands))`.

## Owner rulings (recorded 2026-10-21)

- **R1, skipped questions:** a draft may include explicitly skipped questions. **Approval is
  prohibited until they have valid answers.**
  - A skipped active question is draft-eligible and enters `basedOn` with
    `validity: "skipped"`.
  - Approval is refused while any basis entry is skipped.
  - Answering the skipped question changes its `answerRev` and `validity`, so the revision's
    basis is no longer current. The path to approval is: answer, then draft a new revision,
    then approve it.
  - `currency` can be `current` only when every basis entry is `valid`.
- **R2, inactive questions:** the plan basis covers the **active branch**.
  - Inactive questions in the named sessions are excluded without error.
  - A branch change (a basis question deactivates, or an inactive question activates) or a new
    active question makes the approval not current.
  - Edits confined to inactive questions do not affect currency.

### P3.2 Hashing and rules (`server/plan-hash.ts`, `server/plan-rules.ts`; READY)

```ts
// plan-hash.ts
export type BasisEntry = PlanRevision["basedOn"][number];
export function activeBasis(sessions: Session[], sessionIds: string[]): Ref[];   // active questions of sessionIds, sorted by refKey
export function basedOnSnapshot(sessions: Session[], sessionIds: string[]): Array<BasisEntry & { value: { optionId?: string; text?: string } }>;
export function decisionSnapshotHash(sessions: Session[], sessionIds: string[]): string;
export function contentHash(rev: Pick<PlanRevision, "markdown" | "tasks" | "basedOn" | "decisionSnapshotHash">): string;

// plan-rules.ts
export function eligibility(sessions: Session[], sessionIds: string[]): { basis: Ref[] } | { error: DomainError };
export type Currency = { status: z.infer<typeof ApprovalStatus>; reasons: string[] };
export function basisCurrent(sessions: Session[], sessionIds: string[], revision: PlanRevision): { ok: boolean; reasons: string[] };
export function currency(sessions: Session[], plan: Plan, receipt: ApprovalReceipt | null, copyOnly: boolean): Currency;
export function taskTransition(from: TaskState["status"], to: TaskState["status"], ctx: { origin: WriteOrigin; note?: string; current: boolean }): DomainError | null;
```

Rules:
- **`eligibility`**:
  - An unknown session id → `not_found`.
  - The basis is `activeBasis(sessions, sessionIds)`. Inactive questions are ignored (R2).
  - Every basis question must be `valid` or `skipped` (R1). Active `unanswered` or `stale`
    questions → `plan_ineligible` with `details.refs` and `details.reasons`.
  - An empty active basis → `plan_ineligible` with reason "no active questions".
- **`basisCurrent(sessions, plan.sessionIds, revision)`** gives `ok: false` with one reason per
  failure:
  - the stored `contentHash` ≠ a recomputation;
  - the recomputed `activeBasis` set ≠ the `revision.basedOn` refs. Reasons:
    `"<ref> became active"` for each new or newly active question, and
    `"<ref> is no longer active"` (R2);
  - any basis entry's `answerRev`, `definitionRev` or `validity` ≠ current;
  - the recomputed `decisionSnapshotHash` ≠ `revision.decisionSnapshotHash`;
  - any basis entry recorded or currently `skipped`: `"<ref> is skipped; answer it and draft a
    new revision"` (R1).
- **`currency`**:
  - no receipt and no copy for the latest revision → `unapproved`;
  - a copy without a valid plugin-data receipt → `unverified`;
  - a receipt whose hashes ≠ the latest revision's → `not_current`;
  - otherwise `current` exactly when `basisCurrent(...).ok`, else `not_current` with its
    reasons.
- **`taskTransition`** implements ruling 7: the allowed edges; `task_transition` otherwise;
  `plan_not_current` for `→ in_progress` when not current; `verified` requires UI origin and a
  note; chat may target only `in_progress` or `done`.

Behaviour:
- `draft`: one `transact(expectedRevision)`.
  - Compute the basis with `eligibility` and snapshot it into `basedOn` (current `answer.rev`,
    `definitionRev`, `validity`) for the active branch, with
    `decisionSnapshotHash(sessions, sessionIds)`.
  - Task ids: keep a supplied `id`, otherwise `newId()`. Duplicate task ids → `invalid_input`.
  - New plan: `id = newId()`, with `revisions`, `approvals`, `taskStates`, `intents` and
    `tickets` all `[]`. Existing plan: append revision `rev = last + 1` and update the plan-level
    `title` and `sessionIds`.
  - Compute both hashes. After the commit, call `syncExport`.
  - A chat or UI origin is allowed; the origin is not stored on the revision (the schema has no
    field, and ruling 1 adds none).
- `approve`: **rejects any origin other than `source: "ui"`** with `invalid_input`
  ("approval only in the Paseo UI"), as defence in depth. The rest follows ruling 6:
  `receiptId = newId()`, `at = now()`. Stale `rev` → `plan_revision_mismatch` with
  `details: { latestRev }`. Hash mismatch → `plan_revision_mismatch`. Not current →
  `plan_not_current` with reasons.
- `taskUpdate`: one `transact(expectedRevision)`. It checks `planRev === latest.rev` and
  `contentHash === latest.contentHash` (`plan_revision_mismatch`), then
  `taskId ∈ latest.tasks` (`not_found`). It applies `taskTransition` with
  `current = currency(...).status === "current"` and upserts the `TaskState` for
  `(latestRev, taskId)`. `verified` stores `verification: { at, note }`.
- `get`/`list`: read-only, except the best-effort export repair in `get` (ruling 3). Receipts are
  read for the latest revision and for each copy.

  conditional on an unselected option → still `current`.

### T3.4 Receipts (`server/approvals.test.ts`, READY)

- Write then read round trip. `nodeApprovalFs.mode` gives `0o600` for the file and `0o700`
  for every directory level under `approvals/`.
- A second write for the same rev returns `created: false` and the existing receipt; the file
  bytes are unchanged.
- **Two concurrent writers** (`Promise.all` of two `write` calls with different `receiptId`s
  for the same rev, on two `ApprovalStore` instances over one `stateDir`): exactly one
  `created: true`. Both results return the **same** stored receipt, and the file holds the
  winner's bytes.
- **Partial write:** an `ApprovalFs` wrapper that throws after the temp file is written and
  before `link` → `write` rejects, `read` gives null and no final file exists. A later `write`
  succeeds, and a temp file older than 60 s is removed.
- `link` throwing `ENOTSUP` → `write` rejects, and no final file exists (no rename fallback).
- A receipt file whose `projectId` differs from its path → `read` gives null and the log has
  "receipt invalid".
- An id containing `../` → `unsafe_root` before any fs call (recording fs).
- Survives a restart: a new `createApprovalStore` on the same `stateDir` reads it.
