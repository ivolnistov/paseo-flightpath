# Decision Roadmap plugin: architecture specification

Status: consolidated design draft, 2026-10-20. Owner-approved direction is in README.md and
AGENTS.md; this document turns it into interfaces and boundaries. Implementation cards are in
`docs/plans/2026-10-20-decision-roadmap.md`. Open owner choices are listed in section 12.

## 1. Goal

A trusted local Paseo plugin that lets the owner run branching decision interviews ("grilling
sessions") for a project, see them as a visual roadmap inside Paseo, answer questions either in
the UI or in agent chat, keep every answer revision, mark dependent decisions stale when an
upstream answer changes, approve a specific plan revision, and mirror approved execution tasks
to an optional tracker (SnailOrbit first).

## 2. Verified platform constraints (Paseo 0.12.0, SDK `@getpaseo/plugin` 0.12.0)

Verified on 2026-10-20 against https://paseo.sh/docs/plugins/reference.md, the installed CLI
(`paseo --version` = 0.12.0, SDK package at
`/opt/homebrew/lib/node_modules/@getpaseo/cli/node_modules/@getpaseo/plugin`) and the locally
installed `excalidraw` plugin, which is a working precedent on this daemon.

- A plugin has a client entry (`index.client.tsx`, React Native primitives only, runs in desktop,
  web, iOS and Android apps) and a server entry (`index.server.ts`, Node subprocess inside the
  daemon). `shared/` holds Zod contracts only.
- Client to daemon communication is typed RPC (`defineRpc` + `server.handle` + `useRpc`). There is
  no push channel from server to client; live updates use TanStack Query polling with
  invalidation after mutations (the excalidraw plugin polls every 5 s).
- Server hooks: `server.before("agent.create")` can add `mcpServers` to a new agent's config. The
  daemon rejects MCP config for providers without MCP support, so injection is gated to known
  providers (`claude`, `codex`, `opencode`, `copilot`). `McpServerConfig` supports `stdio`, `http`
  and `sse`. Hooks only apply to newly created agents, not already-running ones.
- `server.on("agent.turn_ended")` exists and can refetch the timeline tail; it is best effort,
  not persisted, and not required by this design.
- A server handler can append a plugin-owned timeline row (`timeline.append`, re-append with the
  same `id` to update; 64 KiB data cap; rows do not survive a daemon restart). A client
  `addTimelineRenderer` draws it.
- Workspace panel props give `workspaceId`; `useWorkspace(id, selector)` exposes `directory`,
  `projectRootPath`, `kind` (`directory | local_checkout | checkout | worktree`). Do not use RPC
  to discover the current workspace.
- UI: `theme.colors.*` for every color, `layout.compact` for narrow layouts, `Modal` (bottom sheet
  on compact), `FlatList`/`ScrollView` from `@getpaseo/plugin/client/react-native`, Lucide icons,
  `useToast`. No DOM, no `className`, no React Flow, no arbitrary client npm dependencies.
- Persisted host-scoped settings via `defineSettings` + `registerSettings` + `useSettings`; the
  docs state these are plain JSON and "not a credential vault".
- Plugin install from a host directory: `paseo plugin install /abs/path`; `paseo plugin reload`
  reloads it. No daemon restart is needed or allowed.
- Node dependencies installed in the plugin directory are available to the server runtime only.

## 3. Architecture in one paragraph

One plugin, `decision-roadmap`, with one owner of project data: the plugin server process. It
reads and writes a canonical JSON store inside the project (`<storeRoot>/.decisions/`), exposes it
to the Paseo UI through plugin RPCs, and exposes the same store to agents through an in-process
HTTP MCP server injected into new MCP-capable agents via the `agent.create` hook (the pattern the
installed excalidraw plugin already uses on this daemon). Because UI and chat both write through
the same process and the same store module, they converge by construction; no reconciliation
layer is needed. The UI is a workspace panel built from React Native primitives: a roadmap view
(cards laid out by dependency depth), a question card modal (options, recommendation, free text,
discussion, revision history), and a plan view (revisions, approval bound to a revision hash,
tasks and ticket state). A tracker adapter behind an interface mirrors approved tasks to
SnailOrbit with local mappings and idempotent recovery; remote writes are off by default and each
batch is shown as exact payloads for owner confirmation before sending. The SnailOrbit transport
is not designed here: SnailOrbit is reachable on this machine through an MCP server, its public
API contract is unverified, and the adapter's transport is a bounded evidence task in stage 4.

```
Paseo app (desktop/mobile/web)            Paseo daemon
┌──────────────────────────────┐          ┌─────────────────────────────────────────┐
│ Roadmap workspace panel      │  RPC     │ plugin server subprocess                │
│  overview / session / plan   │─────────▶│  rpc handlers ─┐                        │
│ question card Modal          │◀─────────│                ├─▶ store (JSON, atomic) │
│ timeline renderer (stage 5)  │          │  MCP http srv ─┘      │                 │
└──────────────────────────────┘          │     ▲                 ▼                 │
                                          │     │           <project>/.decisions/   │
   agent (claude/codex/…) ── MCP tools ───┼─────┘                                   │
                                          │  agent.create hook injects MCP URL      │
                                          │  tracker adapter → SnailOrbit (gated)   │
                                          └─────────────────────────────────────────┘
```

## 5. Store location and format

- `storeRoot` is the project root of the workspace (`projectRootPath`) by default; see open
  choice Q1. The store directory is `<storeRoot>/.decisions/` and is meant to be committed.
- Layout:
  - `.decisions/roadmap.json`: `{ version: 1, sessions: [{id,title,status,file}], plans: [{id,title,file}], links: Link[] }`
  - `.decisions/sessions/<sessionId>.json`: full Session.
  - `.decisions/plans/<planId>.json`: full Plan including all revisions, approval and ticket mappings.
  - `.decisions/plans/<planId>.md`: generated, read-only Markdown of the latest revision with the
    revision id and content hash in its header. Derived, never parsed back.
- Writes are atomic (write temp file, fsync, rename). One async mutex per storeRoot inside the
  server process. Before each command the store compares file mtimes and reloads if another
  process (git, editor) changed them. The server keeps a per-storeRoot `revision` counter that
  the client polls cheaply.
- IDs are ULIDs. Timestamps are ISO-8601 UTC strings.

## 6. Domain model (shared/model.ts)

```ts
Option      { id, label, description? }
Answer      { rev: number, optionId?: string, text?: string, source: "ui" | "chat",
              actor: { kind: "human" | "agent", agentId?: string }, at, note?: string,
              quoted?: string /* human chat text an agent relayed */ }
Ref         { sessionId: string, questionId: string }
Activation  { parent: Ref, optionIds: string[] }          // conditional branch: active only when parent's current answer is one of optionIds
Invalidation{ upstream: Ref }                              // dependency: a value change upstream marks this question stale
Question    { id, order, title, context, options: Option[], recommendedOptionId?, allowFreeText: boolean,
              activatedBy: Activation[], invalidatedBy: Invalidation[],
              answer?: Answer /* current */, revisions: Answer[], discussion: Note[],
              status: "open" | "answered" | "stale" | "skipped" | "inactive",
              stale?: { causeQuestionId, causeRev, at } }
Note        { id, at, actor, text }
Session     { id, title, createdAt, status: "active" | "closed", questions: Question[] }
Link        { id, kind: "informs" | "supersedes", from: Ref | { sessionId }, to: Ref | { sessionId }, note? }  // descriptive only, no propagation
PlanRevision{ rev, createdAt, contentHash, markdown, tasks: TaskDraft[], basedOn: { sessionId, questionId, rev }[] }
Approval    { planRev, contentHash, at, actor: { kind: "human" }, note? }
Task        { id, title, description, status: "todo" | "in_progress" | "done" | "verified",
              verification?: { at, note }, ticket?: TicketMapping }
TicketMapping { provider: "snailorbit", remoteId, remoteKey, url, idempotencyKey, state: "pending" | "created" | "closed" | "unknown", lastSyncAt }
Plan        { id, title, sessionIds: string[], revisions: PlanRevision[], approval?: Approval, tasks: Task[] }
```

Rules (implemented in `shared/graph.ts` and `server/sessions.ts`, all unit tested):

Three relation kinds are kept distinct in data, in propagation and in the UI:

- Conditional activation (`activatedBy`): a question is `inactive` unless every activation
  parent has a current answer whose `optionId` is in `optionIds`. Activation is recomputed after
  every answer change; a question that becomes inactive keeps its answers and revisions and
  returns to its previous status when the branch is active again. Inactive questions never
  count as open or stale, and are drawn dimmed on the roadmap.
- Dependency invalidation (`invalidatedBy`): when a question's current answer changes value
  (different `optionId` or text), every transitive downstream question reachable through
  `invalidatedBy` edges that has an answer becomes `stale` with the cause recorded. Activation
  edges do not propagate stale marks by themselves; a parent whose change should also
  invalidate a child carries both edge kinds (the authoring commands accept both).
- Descriptive links (`Link`, `informs` / `supersedes`, question- or session-level, including
  cross-session): shown on cards and in the overview, never propagate anything.

- Answering appends a new `Answer` revision; `answer` points at the latest. Revisions are never
  deleted. Changing an answer from the UI or chat is the same command.
- A `confirm` command on a stale question records a new revision with the same value and clears
  `stale`.
- A plan revision records the answer revisions it was based on. If any of those questions gets a
  newer revision, the plan's `approval` remains in history but `plans.status()` reports
  `approvalCurrent: false`; ticket creation and task execution require `approvalCurrent: true`.
- Approval is only accepted with an explicit `{ planId, rev, contentHash }` that equals the latest
  revision. There is no MCP tool for approval, and no approval field in any imported file is
  honoured: approval is written only by the `plan.approve` RPC called from the plugin UI.

## 7. RPC contracts (shared/rpc.ts)

All inputs carry `storeRoot: string`, validated server-side against Paseo workspaces
(`paseo.workspaces.list`) so the plugin never touches arbitrary directories.

| RPC | Input | Output |
| --- | --- | --- |
| `roadmap.version` | storeRoot | `{ revision, exists }` |
| `roadmap.init` | storeRoot | `{ created: boolean }` |
| `roadmap.overview` | storeRoot | sessions summary (counts open/answered/stale/inactive), plans summary (latest rev, approvalCurrent), links |
| `session.get` | storeRoot, sessionId | Session with computed `status` per question, `depth` for layout (longest activation/invalidation path from a root) and resolved link labels |
| `session.create` | storeRoot, title | `{ sessionId }` |
| `question.create` | storeRoot, sessionId, title, context, options, recommendedOptionId?, allowFreeText, activatedBy, invalidatedBy | `{ questionId }` |
| `question.answer` | storeRoot, sessionId, questionId, optionId? \| text?, note? | `{ rev, staleMarked: string[] }` |
| `question.confirm` | storeRoot, sessionId, questionId | `{ rev }` |
| `question.discuss` | storeRoot, sessionId, questionId, text | `{ noteId }` |
| `question.skip` | storeRoot, sessionId, questionId, note? | `{}` |
| `link.create` / `link.delete` | storeRoot, Link | `{}` |
| `plan.get` | storeRoot, planId | Plan + `approvalCurrent` |
| `plan.draft` | storeRoot, planId?, title, sessionIds, markdown, tasks | `{ planId, rev, contentHash }` |
| `plan.approve` | storeRoot, planId, rev, contentHash, note? | `{ approvedAt }` or error `plan_revision_mismatch` |
| `task.update` | storeRoot, planId, taskId, status, verification? | `{}` |
| `tracker.preview` | storeRoot, planId | `{ actions: [{ taskId, kind: "create" \| "close" \| "skip", payload, reason }] , mode }` |
| `tracker.apply` | storeRoot, planId, actionIds, confirmToken | `{ results: [{ taskId, state, remoteKey?, error? }] }` |

`tracker.apply` requires the `confirmToken` returned by the immediately preceding
`tracker.preview` for the same action set; this is how the UI confirmation of exact payloads is
enforced server-side.

## 8. MCP tools (server/mcp-tools.ts)

Endpoint: in-process HTTP MCP server on `127.0.0.1`, random port and secret persisted under
`$PASEO_HOME/plugin-data/decision-roadmap/mcp.json`; the URL path embeds an HMAC-signed
`storeRoot`, so a tool call can only touch the project it was issued for (same scheme as the
excalidraw plugin). Injected by `server.before("agent.create")` when the provider supports MCP and
the resolved storeRoot has a `.decisions/` directory (see Q3).

| Tool | Purpose |
| --- | --- |
| `roadmap_overview` | sessions, open/stale questions, plans and approval state |
| `roadmap_get_session` | full session with statuses |
| `roadmap_ask` | create one or more questions with options, recommendation, free-text flag, activation conditions and invalidation dependencies; returns ids |
| `roadmap_answer` | record an answer with `source: "chat"`, `actor.kind: "agent"`, and the quoted human text; same validation as the UI |
| `roadmap_confirm` | clear a stale mark by re-confirming |
| `roadmap_discuss` | append a discussion note |
| `roadmap_link` | create a descriptive `informs`/`supersedes` link |
| `roadmap_plan_draft` | create a new plan revision from answers |
| `roadmap_plan_status` | approval state, `approvalCurrent`, task and ticket states |
| `roadmap_task_update` | move a task to `in_progress`/`done` (never `verified`) |

Deliberately absent: approve, ticket create, ticket close, delete anything. Tool descriptions
tell the agent that answers it records on the human's behalf must quote the human and that
approval happens only in the Paseo UI.

## 9. Settings (shared/settings.ts, host scope)

```ts
{ injectMcp: "opted-in-projects" | "all-agents" | "off",
  tracker: { provider: "none" | "snailorbit", mode: "dry-run" | "live", projectKey?: string } }
```
Defaults: `injectMcp: "opted-in-projects"`, `tracker.provider: "none"`, `mode: "dry-run"`.
Transport-specific fields (endpoint, credential handling) are added by the stage 4 evidence task
once the SnailOrbit public API contract is verified; nothing secret is stored in settings.

## 10. Client UI

Workspace panel `roadmap` (`context: "workspace"`, `locations: ["workspace", "explorer"]`), a
Command Center item "Open decision roadmap", and a client slash command `/roadmap` that opens the
panel (stage 5). Everything is built from `View`, `Text`, `Pressable`, `TextInput`, host
`ScrollView`/`FlatList`, `Modal`, `Icon`, `useToast`.

- Overview: list of sessions with status counts and plans with approval state; "Initialise
  roadmap" when the store does not exist.
- Session view (the visual roadmap): questions grouped by dependency depth. Wide layout: columns
  per depth with cards in order; activation edges drawn as thin `View` connectors with the
  triggering option label, invalidation edges as dashed-style muted connectors, descriptive links
  as a footer line on the card. Connectors are plain `View` rows between adjacent depth columns
  (no canvas, no SVG dependency). Compact layout: one column, children indented under their
  parent with a left border; connectors omitted, relations shown as "active when: …",
  "invalidated by: …" and "linked: …" lines. Card: title, status chip (open/answered/stale/inactive/skipped), current answer
  summary, "recommended" badge if unanswered.
- Question card modal: context text, numbered options as Pressables with the recommended one
  highlighted, optional free-text `TextInput`, "Answer", "Confirm" (stale only), "Skip";
  discussion list with add note; revision history list with source/actor/time.
- Plan view: revision list with hash prefix, Markdown rendered as plain `Text` blocks, "Approve
  revision N" button (disabled when not latest), approval badge and `approvalCurrent` warning,
  task list with status controls, "Preview tracker actions" opening a confirmation modal that
  shows exact payloads and the live/dry-run mode before "Apply".
- Freshness: `roadmap.version` polled every 3 s while the panel is mounted; data queries are
  invalidated when the revision changes or after any mutation.

## 11. Delivery boundaries

Distinct states, reported separately and never merged: (1) validation = `tsc --noEmit`, vitest,
the RN audit grep from the paseo-plugin skill; (2) review = Kimi read-only review of the diff
and KensAI gate on the exact final revision; (3) installation = `paseo plugin install
<worktree path>` (no daemon restart), the plugin listed and enabled under Settings → Plugins and
`paseo plugin logs decision-roadmap` clean; (4) UI verification = the panel exercised on the
desktop layout and on a compact viewport (Paseo browser tools against the web UI, resized)
with screenshots as evidence. The coordinator owns (3) and (4) and reports them with evidence;
the owner is asked only for decisions, for `mode: "live"` and for confirming each tracker batch
in the preview modal. Installing the plugin on the live daemon is a coordinator action under
the AGENTS.md rules (no restart, no approval-setting change).

## 12. Open owner choices (recommendation marked)

Q1 Store location. (a) project root `projectRootPath`, one roadmap per project shared by all
worktrees (recommended: decisions precede branches; execution worktrees read one source);
(b) the workspace directory, so a worktree carries its own copy and git merges it.

Q2 MCP injection scope. (a) inject tools only into agents whose project has `.decisions/`
(recommended: no tool-prompt noise in unrelated projects); (b) every MCP-capable agent on the
daemon, like the excalidraw plugin; (c) off until enabled in settings.

Everything else in this document uses already-approved decisions or conventional defaults.
Tracker transport and credential handling are deliberately not an owner question yet: they
depend on the verified SnailOrbit API contract gathered in the stage 4 evidence task.
