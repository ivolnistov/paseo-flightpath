**Goal:** Extend the shipped Decision Roadmap plugin (Stages 0–5, feature `feb6905`) into the
approved Firstmate-replacement redesign: an ordered feature roadmap, per-feature approved plans
with ordered tasks, explicit dependencies, parallel grants, human-owned DoD, mandatory grilling,
a per-feature coordinator in an isolated worktree with safe pause, rework and trusted completion
evidence.

**Architecture:** The existing local canonical store (`<storeRoot>/.decisions/`, snapshot
generations, one manifest) is extended to schema version 2 by a read-side projection that never
rewrites v1 payloads or hashes; v2 records (features, runs, delegations, project settings) are new
files inside each generation. The plugin server owns every rule (readiness, completion predicate,
evidence binding, pause acknowledgement, stale-run rejection) behind RPCs for the UI and MCP tools
for agents; the coordinator agent pulls ready tasks and reports progress, never decides
completion. The React Native client gains a roadmap screen, a feature screen with its own
timeline-and-composer chat (tasks left, chat right on wide; separate screens on phone) and
plan-preview fields, reusing the existing panel, hooks and theme helpers.

**Tech Stack:** TypeScript, Zod 4, `@getpaseo/plugin` 0.12.0 (host-provided; server runtime
values from `@getpaseo/plugin/server`, client from `@getpaseo/plugin/client`), `@getpaseo/client`
and `@getpaseo/protocol` 0.12.0 types (protocol schema values already bundle, proven in Stage 5),
React Native 0.81 plugin client, vitest 5, MCP SDK 1.32.1, Node `node:fs/promises`; no new
dependencies.

**Spec:** `docs/plans/2026-10-23-firstmate-redesign-design.md` (approved 2026-10-26, SHA-256

`.sdd/ui-mockups/grilling-coordination.md`; `docs/SPEC.md` for the preserved baseline.

## Global Constraints

- Preserve all shipped Stage 0–5 behaviour and the existing `.decisions` data; v1 payloads,
  `changeToken`, `contentHash` values and approval receipts are never rewritten; nothing newly
  mandatory is enforced against previously accepted records (design §1).
- Approval is a UI action on an exact plan revision; no MCP tool approves, sets `verified`,
  deletes, cancels, defers or reorders (design §1, §6).
- Start authorisation: UI Start control, or an explicit, scoped, revocable human delegation given
  in chat and verified against that chat's host timeline; approval alone never starts; stop and
  pause always win (design §3.1, §6).
- Roadmap is an ordered feature list; six feature statuses only; no built/not-built field.
- Feature and plan are always grilled; a task's grill checkbox (human or MCP agent) is mandatory
  when set; all required grilling completes before approval; bug grilling optional; WTR optional.
- Every human-defined DoD criterion of a task is evaluated with trusted evidence; independent
  review and required checks are mandatory regardless of DoD text; human acceptance is required
  only where the approved completion policy says so (design §3.5, Q7=4, Q29=1).
- Repair ceiling 30 failed verification/review cycles per task by default, configurable, explicit
  additional budget, no silent reset, no oscillation detector.
- No model, agent profile or review provider is hard-coded in the product.
- Mobile/compact and themes stay usable; no browser DOM, no React Flow, no arbitrary npm client
  dependencies inside the RN plugin client.
- Production code in isolated worktrees after plan approval; production and test files have
  separate Opus owners; one subscription worker at a time; exact-revision ordinary KensAI gate per
  stage; no cumulative end review; never restart the daemon; install/reload and UI acceptance are
  separate owner-authorised states distinct from typecheck, Hermes parse and test green.
- Repository-authored content is strictly English: README, OVERVIEW, documentation, plans, task
  cards, reports, code comments and product-supplied UI text; human conversation with the owner
  stays in Russian; user-authored project data keeps its original language (owner rule,
  2026-10-26).
- Durable history (feature events, run records, evidence) is append-only and never capped or
  compacted; `keepGenerations` bounds snapshot count only, never the content of the current record.

## 1. Technical choices settling design §9

| Topic | Choice | Why |
|---|---|---|
| Schema v2 and legacy projection | `RoadmapMeta.version: 1 \| 2`. Reading: v1 raw payload is parsed with the v1 schemas and its `changeToken` verified on the raw canonical form first; then `projectV1(data)` builds the in-memory v2 view with `features: []`, `runs: []`, `delegations: []`, `settings: {}`; legacy sessions and plans are returned unchanged. "Legacy" is a derived predicate, never a stored field: a legacy plan is one whose `featureId` is absent, a legacy revision one whose `schema` is absent, and a legacy session one whose `blocks` are absent (`effectiveBlocks(session)` computes a synthetic block view on read). No `legacy` or `legacyBlocks` marker is written, because the same rule requires legacy objects to be stored verbatim (clarified after R0 review c0002). Writing: v2 generations store sessions and plans verbatim as read (v1 revisions keep their exact task objects, hash and receipts); new records are separate files `features/<id>.json`, `runs/<id>.json`, `delegations.json`; `meta` becomes v2 with `featureIds`, `runIds`, `settings`. `changeToken` of a v2 generation is computed over the v2 canonical form. | No v1 payload or hash is altered; receipts stay valid. |
| Versioned revision hashing | `PlanRevision` gains `schema?: 2`. `contentHash` for revisions without `schema` is the existing v1 function over the three-field tasks; for `schema: 2` revisions it hashes the v2 task objects. `plan-rules.basisCurrent` and approval currency use the function matching the revision. Legacy plans accept `task.update`, tracker and approval currency exactly as today; DoD/grilling gates apply only to `schema: 2` revisions. Legacy compatibility (reconciled 2026-10-27 with the owner-acknowledged R1.0 path): an unbound legacy plan may keep being re-drafted on the legacy path (no `featureId`, no v2 task field) and stays legacy with its shipped re-draft flow intact; a legacy plan migrates to v2 only by an explicit binding, a `plan.draft` that supplies `featureId` (and may supply v2 fields), which creates its first `schema: 2` revision; from then on the plan is bound: every later draft of that plan must carry the same `featureId` and is `schema: 2`; omitting `featureId`, changing it, or drafting a legacy-shaped revision for a bound plan → `invalid_input` (no downgrade, no rebind). | Settles the R0.1 default contradiction without touching accepted records; preserves the shipped legacy re-draft flow while gating every v2 revision. |
| Task fields (v2) | `TaskDefinitionV2 { id, title, description, dependsOn: Id[], parallel: boolean, completion: "auto" \| "human", grill: boolean, grillSessionId?: Id, dod: string }`. `dod` may be empty in a draft; approval requires non-empty. | Draft freedom, approval gate. |
| Project DoD template sources | File `<storeRoot>/dod template.md` (exact spelling; must be a regular non-symlink file), else `meta.settings.dodTemplate` (project, in the store), else host setting `roadmap.dodTemplate` (global). First found wins, no merge; `{ source, text }` returned to UI and MCP. | Q31=1; host settings are `scope: "host"` only. |
| DoD evaluation (every criterion) | `parseDod(text)` yields items: `- [check] <command>` → automated check run by the server; any other non-empty line → review criterion. Evidence per task run: (a) every check item has a server-recorded pass; (b) the configured independent review returns a structured verdict with a pass for every review criterion and for the task as a whole; (c) when `completion === "human"`, a UI acceptance. Review is run always, even when the DoD has no text items. Nothing is informational. | Design §3.5, Q7=4, Q29=1; no self-attestation, no unchosen human gate. |
| Result binding | Every evidence item carries `ResultBinding { taskId, planId, planRev, contentHash, runToken, worktree: WorktreeIdentity }` where `WorktreeIdentity { headCommit, indexTreeHash, worktreeTreeHash, untrackedHash }` is computed read-only by the server in the feature worktree: `headCommit` = `git rev-parse HEAD`; `indexTreeHash` = sha256 over the canonical bytes of `git ls-files --stage -z` (mode, blob id, stage, path per entry, in git's order; no index copy and no object writes, so it works in linked worktrees where `.git` is a file); any entry with stage ≠ 0 (unmerged) makes the identity invalid and the task run `evidence_not_ready` until resolved; `worktreeTreeHash` = `git diff HEAD --binary --no-color` content hashed; `untrackedHash` = sha256 over the sorted list of `git ls-files --others --exclude-standard -z` entries, each as `path`, file type and sha256 of file content (deleted-since-listing entries recorded as `missing`). Excluded by explicit scope: `.decisions/` and the plugin's own evidence/log directory, so recording evidence never invalidates itself; nothing else is excluded, untracked code included. The identity is taken immediately before a check or review starts and again immediately after it ends; any difference, or a mismatch with the task run's current identity, invalidates that result (stored as `lateEvidence` with reason `worktree_drift`). Exit code alone never passes anything: checks pass only with exit 0 **and** matching binding; review passes only with a parsed verdict **and** matching binding. | Audit finding 1; stale-event rule. |
| Review provider contract | Host setting `roadmap.reviewCommand` (deployment configuration, any tool or model). The server runs it with `spawnProcess(command, args, { cwd: worktree, env, stdio: "pipe" })` (verified: `execCommand` has no stdin option; `spawnProcess` with `stdio: "pipe"` returns a `ChildProcessWithoutNullStreams`), writes `ReviewRequest { binding, dod: { items }, taskTitle, taskDescription }` as JSON to `child.stdin` then ends it, collects stdout and stderr up to `maxBuffer`, enforces `reviewTimeoutMs` with `terminateProcess` on timeout, pause, rework or cancel, and parses `ReviewVerdict { binding, verdict: "pass" \| "fail", items: Array<{ index, verdict, note }> , summary }` from stdout; a missing, unparsable or mismatched-binding verdict is a fail. This is a plugin-defined integration contract, marked as a technical choice. | No hard-coded reviewer; structured, bound evidence. |
| Process bounds | Technical defaults in host settings: `checkTimeoutMs` 600000, `reviewTimeoutMs` 1800000, `maxBuffer` 10 MB; on pause, rework or cancel the runner calls `terminateProcess`. These are runner bounds, not owner spend policy. | Required by `execCommand`. |
| Coordinator binding and isolation | `feature.coordinator { agentId, workspaceId, boundAt, profileRef }`. UI Start with no binding: `paseo.workspaces.create({ source: { kind: "worktree", cwd: storeRoot, projectId, action: "branch-off", refName: <base branch from host settings or current HEAD> }, agent: { config: mapProfile(profile), title, labels: { "decision-roadmap.feature": featureId }, prompt } })`. The user picks a saved profile from `paseo.config.get()` in the Start dialog; the plugin stores the profile reference only. Attach existing: binds the calling agent through the verified grant→agent binding. Replace: explicit handover action, old binding kept in history. | R2; one coordinator per feature (Q19). |
| Grant → agent binding | `before("agent.create")` injects `PASEO_ROADMAP_GRANT_FP=<fingerprint(grantId)>` into `request.env` next to the MCP URL; `before("agent.session_open")` reads `env` and `agentId` and records `grant.agentId`; `agent.turn_started` supplies the active `turnId`. Tools that need a chat identity refuse when the grant has no bound agent. | Provenance audit §A. |
| Delegated start provenance | `roadmap_start { scope: "feature" \| "roadmap", featureId?, quoted }` requires a bound agent; the server refetches that agent's timeline tail (`projection: "canonical"`), finds a `user_message` whose text does not start with `<paseo-system` and contains `quoted` verbatim, and records `DelegationProvenance { agentId, messageId?, seqStart, turnId?, timestamp, quoted }`; otherwise `DomainError("delegation_unverified")`. The delegation is appended as a timeline row in that chat with scope and a Revoke control, and shown on the roadmap screen. Residual risk stated in §0. | Audit finding 3. |
| Dispatch | Pull model: `roadmap_run_next { runToken }` computes ready tasks under readiness and parallel grants; `roadmap_task_claim` refuses unless the run is running and the task ready. | Server owns the rules. |
| Stale events | Each run has `runToken` (ULID); all run-scoped MCP mutations carry it; mismatch → `run_stale`. | Design §3.3 item 4. |
| Pause protocol | 1) `run.state = paused`, claims refused, runner processes terminated; 2) steer message to the coordinator (`send(text, { activeTurnBehavior: "steer" })`) asking every active worker to suspend at its nearest safe point and call `roadmap_run_ack`; 3) `paused (acknowledged)` only when every active task run acknowledged, else `paused (awaiting N)` with the unresolved list; 4) late events → `lateEvidence`; 5) resume and replacement re-run readiness. A forced interrupt (`send` without `activeTurnBehavior`, or `paseo stop`) is **not** part of pause; see §8 for the single owner tradeoff. | Design §3.3; R1 facts. |
| Task cancellation | `TaskState.status` gains `"cancelled"` (v2; `PlanV1` keeps the strict four-value `TaskStateV1`); `task.update` input excludes `cancelled` only (the shipped UI `verified`-with-note path is preserved, R2 card G3); `roadmap_task_update` stays `in_progress \| done`; `taskTransition` rejects any manual move to or from `cancelled`; only rework and feature cancellation set it. | No per-task cancel action (design §2); shipped verification flow unchanged. |
| `StoreFs` regular-file check | `StoreFs.lstat` result type gains `isFile(): boolean`; `nodeStoreFs` passes Node `Stats` through; `fault-fs.ts` wraps unchanged; test fakes that return lstat objects add `isFile`. | Needed for `dod template.md`. |
| Timeline and slash | Existing observer gains run and feature rows; `/roadmap feature|start|pause|bind` open the UI controls; slash commands never start execution themselves. | Design §6. |
| Tracker | Intents keep `{ planRev, taskId }`; the ticket description includes the DoD text for v2 revisions; no transport change. | No tracker contract change. |

## 7. Risks

- Provenance: a local un-enveloped SDK or CLI send is indistinguishable from a UI message in the
  host timeline; mitigations are the real-message requirement, the visible delegation row with
  Revoke, and the trusted-local-agent assumption. No cryptographic origin is claimed.
- Pause latency: steer plus acknowledgement can wait on a long turn; the run shows "awaiting"
  with the unresolved list; no forced stop is part of the approved safe pause.
- Review provider contract: a structured verdict over piped stdin/stdout is a plugin-defined
  integration; providers that cannot emit it need a wrapper script, which is deployment work.
- Client chat: rendering the timeline inside the panel depends on `usePaseo()` behaving inside a
  workspace panel as it does in Firstmate's screens; R4.1 is the first task to prove it, with
  install/reload acceptance as the evidence state.
- Store growth: run records are append-only by constraint; large features produce large
  generation files; `keepGenerations` bounds snapshot count only. If size becomes a problem, a
  separate owner decision is needed before any compaction.
- Legacy plans stay outside the roadmap (no feature); visible in the Plans list; no automatic
  grouping.

## 8. Optional future feature (out of scope, not required for approval)

- **Immediate interrupt control.** The host supports an immediate turn interrupt (`send`
  without `activeTurnBehavior`, or `paseo stop`). The approved safe pause (steer plus
  acknowledgement, no forced stop) ships as designed; an extra "interrupt now" control is not
  planned and no UI for it is included. It is listed only so the capability is not mistaken for
  part of pause.

No product behaviour beyond the approved design is introduced; every item in §1 is a technical
choice inside it. No owner decision is required to approve this plan.
