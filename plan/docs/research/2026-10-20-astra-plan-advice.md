Fable — ranked advisory corrections below, based on the four requested files. These are planning suggestions, not an approval gate.

1. **Make owner approval durable and authoritative.**
   **SPEC §§5–7; Plan Task 3.1.** “No imported approval is honoured” conflicts with reloading approvals from agent-editable JSON. Define a server-owned approval receipt outside the editable project store, or a signed receipt whose key remains outside it. Bind it to project identity, plan ID, revision, canonical content hash and decision snapshot. Preserve approval history explicitly; the current singular `approval?` cannot retain successive approvals. Define the hash inputs to include task definitions and `basedOn`. Recheck authority when starting execution or applying tracker actions. Test restart, edited JSON, copied receipts, changed tasks and stale dependencies.

2. **Specify transactional storage and conflicting writes.**
   **SPEC §§3,5,7; Plan Task 0.3.** One process and a mutex serialize cooperating requests, but do not guarantee convergence with external editors or atomic updates across session, index and plan files. Choose a recoverable transaction mechanism: for example, immutable snapshot generations with one atomically replaced manifest. Add expected revisions to mutations so a stale UI or agent cannot silently overwrite a newer answer. Define reload validation, malformed/merged-file handling, durable change tokens and the supported writer boundary. Test interruption between file writes and simultaneous chat/UI edits. Remove “converge by construction; no reconciliation layer is needed” until these boundaries are explicit.

3. **Separate activation visibility from answer validity.**
   **SPEC §6; Plan Task 0.2.** A single `status` cannot represent an inactive question whose preserved answer becomes stale. Store validity separately from computed visibility; reactivation must reveal accumulated staleness rather than restore an obsolete status. Define whether inactive or stale parents can activate descendants; recommend requiring active, valid parent answers. Preserve the existing distinction that activation alone does not invalidate answers. Specify unresolved references, cross-session identities, and cycle rejection for the combined activation/invalidation graph used by layout. Add tests for A→B→A branch switching, invalidation while hidden, stale activation parents and mixed-edge cycles.

4. **Invalidate approval on changed decision meaning, not only answer revision numbers.**
   **SPEC §§6–7; Plan Task 3.1.** An upstream change can make a referenced answer stale without incrementing that answer’s revision. Current rules could therefore leave approval current. Bind the snapshot to relevant validity, activation and question/option definitions, or conservatively reject approval currency when referenced decisions become stale or materially change. Define eligible draft inputs, including unanswered, skipped and inactive questions. Task execution status must reference the approved task definition rather than a separately mutable task description.

5. **Complete MCP onboarding and capability boundaries.**
   **SPEC §§2,8,12; Plan Tasks 2.1–2.2.** Creation hooks exclude existing agents and agents created before `.decisions/` initialization. Add a bounded platform-contract investigation and an explicit supported attach/reconnect workflow or documented limitation; test it alongside new-agent injection. A persisted port needs collision/reload recovery, not merely a stable-URL assertion. Bind capabilities to canonical project identity and authenticated agent context; a tool argument or quoted human text is attribution, not authentication. Do not assume an undocumented identity header exists.

6. **Model ambiguous tracker operations before claiming duplicate prevention.**
   **SPEC §7; Plan Tasks 4.0–4.2.** Define durable operation intents separately from confirmed mappings: pending creation has no `remoteId`. Persist exact payload, destination, approval receipt, operation ID and reconciliation state before sending. Search returning no match after timeout does not establish non-creation; require verified idempotency guarantees or retain `unknown` without automatic recreation. Cover ambiguous close/comment operations too. Bind confirmation tokens to exact payloads, destination, mode and current approval; include action IDs and tokens in the RPC schema. Keep tracker delivery explicitly within overall completion.

7. **Align authoring APIs with acceptance steps.**
   **SPEC §§7–8,10; Plan Stage 1 acceptance.** Acceptance creates questions and later adds edges, but the described UI and APIs lack that complete flow. Add bounded question/relationship editing with revision effects, or rewrite acceptance around supported creation operations. MCP also needs an explicit session-creation path.

For Q2, explain separately the effect on new agents and the supported path for existing agents. Do not treat either recommendation as selected.
